Apa yang benar-benar dikirim saat deploy

Deploy bukan mengunggah folder proyek. Kamu mengirim satu transaksi khusus dengan to kosong dan data berisi init code, yaitu bytecode kontrak ditambah argumen constructor yang sudah di-encode. Saat transaksi dieksekusi, EVM menjalankan init code, menyimpan runtime code di alamat baru, lalu menjalankan constructor sekali.

Bentuk transaksi deploy
{
  "from": "0xAlamatWalletDev",
  "to": null,
  "data": "0x6080604052...  (init code + constructor args)",
  "value": "0",
  "gas": "perkiraan dari node",
  "nonce": "urutan transaksi wallet",
  "maxFeePerGas": "...",
  "maxPriorityFeePerGas": "...",
  "chainId": 11155111
}

Alamat kontrak hasil CREATE dihitung dari alamat pengirim dan nonce-nya. Artinya alamat yang sama bisa muncul di chain berbeda jika kamu memakai pengirim dan nonce yang sama, tetapi state dan dananya terpisah. Di Sepolia, alamat itu bisa dibuka di explorer, dipanggil orang lain, dan tetap ada selama jaringan berjalan.

Constructor hanya sekali

Constructor berjalan saat deploy, bukan setiap kali fungsi dipanggil. Nilai yang disimpan ke storage saat constructor akan menjadi state awal. immutable disematkan ke bytecode, sedangkan constant diganti saat kompilasi.

Karena itu, parameter constructor adalah bagian dari identitas kontrak. Kalau kamu mengirim alamat owner yang salah, kontrak tetap ter-deploy dan tetap berfungsi, hanya pemiliknya salah. Tidak ada tombol undo. Kamu harus men-deploy ulang, atau memakai fungsi pemulihan yang memang kamu rancang.

Empat hal yang sering dianggap satu

  • Deploy membuat kontrak ada di chain. Buktinya alamat dan receipt.
  • Verifikasi mengunggah source dan pengaturan kompilasi ke verifier supaya explorer bisa mencocokkan bytecode. Buktinya tab Contract menampilkan source.
  • Hosting frontend menayangkan HTML, JavaScript, dan aset. Buktinya URL yang bisa dibuka.
  • Publikasi source di repositori membagikan kode dan riwayat perubahan. Buktinya commit dan tag.

Kamu bisa punya kontrak ter-deploy tanpa verifikasi, verifikasi tanpa frontend, atau frontend yang menunjuk alamat lama. Rilis yang bisa diperiksa membutuhkan keempatnya konsisten. Inilah alasan tahap ini punya checklist rilis sendiri.

Bab 03FONDASI

RPC adalah pintu masuk. Ia bukan chain itu sendiri.

Wallet, Foundry, dan frontend tidak berbicara langsung ke blockchain. Mereka mengirim request JSON-RPC ke sebuah node, lalu node itu menjawab berdasarkan state yang ia miliki. Siapa yang menjalankan node, seberapa cepat ia sinkron, dan seberapa besar kuotanya, adalah bagian dari sistemmu.

  • Membedakan node, provider, dan wallet provider.
  • Membaca request dan response JSON-RPC dasar.
  • Memilih endpoint untuk latihan dan untuk aplikasi yang dipakai orang lain.
  • Menjaga API key dan memahami batas kuota serta konsistensi data.

Request JSON-RPC yang sebenarnya

Hampir semua yang kamu lakukan di Ethereum, dari membaca saldo sampai mengirim transaksi, bermuara pada JSON-RPC. Bentuknya sederhana: satu method, parameter, dan id request.

Request dan response eth_chainId
curl -s https://ethereum-sepolia-rpc.publicnode.com \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'

# response
{"jsonrpc":"2.0","id":1,"result":"0xaa36a7"}

0xaa36a7 sama dengan 11155111. Kalau endpoint menjawab chain ID lain, endpoint itu bukan Sepolia, apa pun nama yang tertulis di dashboard provider.

Untuk latihan, endpoint publik seperti https://ethereum-sepolia-rpc.publicnode.com atau https://sepolia.drpc.org cukup. Untuk aplikasi yang dipakai orang lain, pakai provider dengan kuota yang jelas dan siapkan fallback. Jangan memakai endpoint publik sebagai satu-satunya jalur produksi.

Contoh URL provider

Alchemy biasanya memakai bentuk https://eth-sepolia.g.alchemy.com/v2/<API_KEY>. Infura memakai https://sepolia.infura.io/v3/<API_KEY>. QuickNode memberi URL khusus per endpoint. Jangan menyalin URL yang berisi key ke dokumentasi, screenshot, atau repositori publik.

API key, kuota, dan 429

Provider menghitung pemakaian dengan compute unit, request per detik, atau kuota harian. 429 Too Many Requests berarti kamu melewati batas, bukan berarti chain mati. Frontend yang baik memberi jeda, mengurangi polling, dan menampilkan pesan yang tenang. Jangan menambah retry tanpa batas; itu hanya memperburuk kuota.

  • Buat key terpisah untuk development, CI, dan produksi.
  • Batasi key produksi dengan domain, IP, atau allowlist bila provider mendukung.
  • Jangan menaruh key berkuota di bundle browser. Pakai proxy server atau key yang memang dirancang publik.
  • Putar key yang pernah terekspos. Menganggapnya rahasia setelah bocor tidak membantu.

Konsistensi dan lag

Provider yang berbeda bisa berada beberapa blok di belakang. Setelah transaksi masuk, satu endpoint mungkin sudah melihat receipt, sementara endpoint lain belum. Ini bukan alasan untuk menandai transaksi gagal. Simpan satu provider untuk alur baca-tulis utama, lalu gunakan fallback dengan hati-hati.

Untuk data historis yang dalam, kamu mungkin membutuhkan archive node. Node biasa bisa membuang state lama. Kalau aplikasi membaca saldo pada blok lama atau menjalankan fork test, pastikan provider mendukungnya.

Memeriksa endpoint sebelum dipakai

Pemeriksaan cepat dengan Cast
export SEPOLIA_RPC_URL="https://ethereum-sepolia-rpc.publicnode.com"

# 11155111

Bab 04PRAKTIK

Wallet development bukan wallet kedua. Ia batas kerja.

Wallet utama menyimpan aset yang tidak boleh hilang. Wallet development menyimpan kunci yang boleh dipakai untuk eksperimen, boleh bocor di lingkungan lokal, dan tidak pernah menyentuh uang nyata. Memisahkan keduanya melindungi aset dan melatih kebiasaan yang benar.

  • Membuat akun khusus untuk deploy dan pengujian.
  • Menyimpan kunci di keystore atau environment, bukan di kode.
  • Memahami peran deployer dan owner kontrak.
  • Mengenali kebiasaan yang membuat kunci bocor tanpa disadari.

Nonce dan satu deployer

Setiap transaksi dari satu akun memakai nonce yang berurutan. Kalau kamu menjalankan dua deploy bersamaan dari akun yang sama, salah satunya bisa memakai nonce yang sudah dipakai, atau menunggu transaksi pertama selesai. Untuk deploy, jalankan berurutan. Kalau perlu paralel, pakai akun berbeda dan catat alamatnya per akun.

src/MiniVault.sol

          
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";
import {Pausable} from "@openzeppelin/contracts/utils/Pausable.sol";
import {ReentrancyGuard} from "@openzeppelin/contracts/utils/ReentrancyGuard.sol";

contract MiniVault is Ownable, Pausable, ReentrancyGuard {
    mapping(address => uint256) public balanceOf;
    uint256 public totalDeposits;

    error ZeroAmount();
    error InsufficientBalance();
    error TransferFailed();

    event Deposited(address indexed akun, uint256 jumlah);
    event Withdrawn(address indexed akun, uint256 jumlah);

    constructor() Ownable(msg.sender) {}

    receive() external payable {}

    function deposit() external payable whenNotPaused {
        if (msg.value == 0) revert ZeroAmount();
        balanceOf[msg.sender] += msg.value;
        totalDeposits += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function withdraw(uint256 jumlah) external nonReentrant whenNotPaused {
        if (jumlah == 0) revert ZeroAmount();
        uint256 saldo = balanceOf[msg.sender];
        if (jumlah > saldo) revert InsufficientBalance();

        balanceOf[msg.sender] = saldo - jumlah;
        totalDeposits -= jumlah;

        (bool ok,) = msg.sender.call{value: jumlah}("");
        if (!ok) revert TransferFailed();

        emit Withdrawn(msg.sender, jumlah);
    }

    function pause() external onlyOwner {
        _pause();
    }

    function unpause() external onlyOwner {
        _unpause();
    }
}

Deploy kontrak tidak punya tarif tetap. Biayanya bergantung pada ukuran bytecode, operasi constructor, harga base fee saat blok dibuat, dan priority fee yang kamu berikan. Estimasi membantu, tetapi estimasi bukan jaminan. Kamu tetap perlu buffer dan receipt untuk mengetahui biaya sebenarnya.

    • 
            
  • Menghitung biaya maksimum dan biaya efektif pada EIP-1559.
    • 
            
  • Membaca estimasi deploy dan menambahkan buffer yang wajar.
    • 
            
  • Memahami mengapa estimasi bisa gagal atau berubah.
    • 
          

        


        
Tiga angka yang jangan dicampur

        

          

            Istilah gas yang muncul di wallet dan explorer.
            
              
IstilahArtinyaDitentukan oleh

            
            
              
Gas limitBatas maksimum gas yang boleh dipakai transaksi.Kamu, wallet, atau estimasi node.

              
Gas usedGas yang benar-benar dipakai saat eksekusi.EVM dan state saat transaksi masuk.

              
Base feeHarga dasar per gas untuk blok tersebut.Protokol, berdasarkan kepadatan blok sebelumnya.

              
Priority feeTip tambahan untuk validator.Kamu atau wallet.

Kalau transaksi memakai lebih sedikit gas dari limit, sisa gas dikembalikan. Kalau eksekusi kehabisan gas, transaksi revert, state tidak berubah, tetapi gas yang sudah dipakai tetap dibayar. Karena itu gas limit terlalu rendah berbahaya, sedangkan gas limit terlalu tinggi tidak selalu mahal.


        
Rumus EIP-1559

        

          
Rumus biaya

          
maxFeePerGas      = baseFee + priorityFee        (atau baseFee * 2 + priority)
effectiveGasPrice = min(maxFeePerGas, baseFee + priorityFee)
biaya maksimum    = gasLimit * maxFeePerGas
biaya efektif     = gasUsed * effectiveGasPrice
refund gas        = (gasLimit - gasUsed) * effectiveGasPrice

        

        
Banyak wallet memakai baseFee * 2 + priorityFee sebagai max fee untuk memberi ruang jika base fee naik beberapa blok. Kamu tidak selalu membayar max fee. Yang dibayar adalah baseFee + priorityFee, dibatasi max fee.

        
Untuk deploy, estimasi awal bisa datang dari eth_estimateGas, forge script, atau panel wallet. Tambahkan buffer 10 sampai 20 persen. Jangan menaikkan gas limit sepuluh kali lipat hanya karena takut gagal; itu membuat wallet menahan saldo lebih besar untuk biaya maksimum.

Kalau kamu memakai max fee baseFee * 2 + priority menjadi 5 gwei, biaya maksimum naik menjadi 0,00125 ETH, tetapi biaya efektif tetap 0,00054 ETH selama base fee tidak naik. Buffer bukan biaya tambahan yang otomatis hilang.

  • Transaksi akan revert karena aturan kontrak, misalnya constructor menolak argumen.
    • 
          
  • Saldo tidak cukup untuk nilai plus gas pada saat estimasi.
    • 
          
  • State berubah antara estimasi dan eksekusi, misalnya orang lain mengubah harga atau status pause.

    • 
          
  • Kontrak terlalu besar dan melewati batas ukuran, sehingga deploy tidak mungkin.

Estimasi yang berhasil bukan janji transaksi akan berhasil. Ia hanya berarti pada state saat itu, dengan gas yang diberikan, eksekusi tidak revert. Selalu baca receipt setelah transaksi masuk.

Transfer ETH biasa memakai 21.000 gas. Deploy menambah biaya untuk calldata, penyimpanan code, dan eksekusi constructor. Kontrak dengan banyak storage atau loop di constructor bisa jauh lebih mahal. Banyak UI hanya punya "loading" dan "berhasil". Padahal transaksi bisa ditolak wallet, menunggu tanda tangan, pending di mempool, masuk blok tetapi revert, diganti dengan fee lebih tinggi, atau hilang dari mempool. Membedakan keadaan ini adalah dasar UX yang jujur.

Tanda tangan bukan pengiriman. Hash bukan bukti berhasil. Receipt dengan status sukses adalah bukti eksekusi. Finality adalah bukti bahwa blok tidak akan diganti oleh reorganisasi.

Kalau status 0x0, transaksi tetap masuk blok dan gas tetap dibayar. State revert, tetapi jejak transaksi ada. Ini berbeda dari transaksi yang ditolak wallet: penolakan tidak pernah dikirim dan tidak punya hash on-chain.


        
Mined bukan final

        
Ethereum bisa mengalami reorganisasi blok. Transaksi yang sudah masuk blok bisa berpindah atau hilang dari canonical chain. Finality protokol terjadi setelah dua epoch, sekitar 12,8 menit pada kondisi normal, ketika checkpoint diterima. Untuk demo testnet, satu atau dua konfirmasi biasanya cukup untuk menampilkan hasil. Untuk klaim yang melibatkan uang atau state penting, tunggu finality atau jumlah konfirmasi yang kamu tentukan sendiri.

        

          Konfirmasi adalah kebijakan aplikasi
          
Tidak ada angka konfirmasi ajaib yang berlaku untuk semua aplikasi. Bursa sering meminta lebih banyak konfirmasi. Kontrak yang hanya menampilkan data bisa memakai satu blok. Tentukan berdasarkan risiko, lalu tulis di UI dan dokumentasi.

        


        
Polling dan langganan

        
Cara paling sederhana menunggu transaksi adalah polling eth_getTransactionReceipt setiap beberapa detik. Wagmi membungkus ini dalam useWaitForTransactionReceipt. Alternatifnya, berlangganan blok baru lewat WebSocket atau eth_subscribe jika provider mendukung.

        
Jangan memakai setTimeout(12000) lalu menganggap transaksi selesai. Blok bisa lebih lambat, provider bisa lag, dan transaksi bisa pending lebih lama. Tunggu receipt atau finality, bukan jam dinding.


        
Nonce, replacement, dan dropped

        
    
          
  • Replacement: transaksi dengan nonce yang sama dikirim ulang dengan fee lebih tinggi. Hanya satu yang akhirnya masuk. Wallet biasanya menawarkan "speed up".
    • 
          
  • Cancellation: kirim transaksi dengan nonce yang sama ke diri sendiri dengan nilai 0 dan fee lebih tinggi. Ini menggantikan transaksi lama jika berhasil.
    • 
          
  • Dropped: transaksi hilang dari mempool karena fee terlalu rendah, node restart, atau batas waktu. Nonce masih bisa dipakai ulang.
    • 
          
  • Stuck: transaksi pending lama karena fee rendah atau nonce di belakangnya belum selesai.
    • 
        

        

          Jangan mengirim ulang tanpa cek nonce
          
Mengirim transaksi baru dengan nonce yang sudah dipakai bisa menghasilkan "nonce too low". Mengirim dengan nonce berikutnya saat transaksi lama masih pending bisa membuat antrean. Cek hash dan nonce di explorer sebelum memperbaiki.

Bab 13PRAKTIK

          
Verifikasi membuat bytecode bisa dibaca manusia.

          
Tanpa verifikasi, explorer hanya menampilkan bytecode dan alamat. Dengan verifikasi, siapa pun bisa membaca source, ABI, dan constructor args yang dipakai. Verifikasi tidak membuktikan kontrak bebas bug. Ia membuktikan bahwa source yang ditampilkan cocok dengan bytecode yang berjalan.

          
    
            
  • Menjelaskan apa yang dicocokkan saat verifikasi.
    • 
            
  • Memverifikasi kontrak dengan Foundry, Etherscan V2, dan Sourcify.
    • 
            
  • Menangani constructor args dan perbedaan pengaturan compiler.
    • 
            
  • Membaca hasil verifikasi dan menolak klaim keamanan yang salah.
    •

            Kalau salah satu berbeda, bytecode tidak akan cocok.

viaIR, metadata hash, dan pengaturan lain juga memengaruhi bytecode. Kalau kamu mengubah konfigurasi kompilasi setelah deploy, verifikasi bisa gagal walau source terlihat sama. Catat pengaturan saat deploy, bukan setelahnya.


        
Verifikasi dengan Foundry

        
Foundry bisa memverifikasi saat deploy dengan --verify, atau setelah deploy dengan forge verify-contract. Untuk Etherscan V2, gunakan chain Sepolia dan API key yang sesuai.

        

          
Verifikasi MiniVault

          
forge verify-contract \
  0xALAMAT_KONTRAK \
  src/MiniVault.sol:MiniVault \
  --chain sepolia \
  --watch \
  --etherscan-api-key "$ETHERSCAN_API_KEY"

        

        
--watch menunggu hasil verifikasi. Tanpa itu, Foundry mengirim request dan keluar. Kalau kamu memakai alias sepolia di foundry.toml, pastikan alias itu menunjuk chain yang benar.

        

          
Verifikasi dengan constructor args

          
# contoh constructor(address admin, uint256 supply)
forge verify-contract \
  0xALAMAT_KONTRAK \
  src/Token.sol:Token \
  --chain sepolia \
  --constructor-args "$(cast abi-encode 'constructor(address,uint256)' \
    0xALAMAT_ADMIN 1000000000000000000000000)" \
  --watch \
  --etherscan-api-key "$ETHERSCAN_API_KEY"

        

        
Di PowerShell, substitusi $(...) tidak berjalan seperti di bash. Jalankan cast abi-encode terpisah, salin hasilnya, lalu tempel sebagai nilai --constructor-args.


        
Etherscan V2 dan Sourcify

        
Etherscan API V2 memakai satu API key untuk banyak chain. Chain dipilih dengan parameter chainid. Sepolia (11155111) tersedia di free tier menurut daftar chain Etherscan per November 2026. Kalau kamu memakai layanan lain, periksa dukungan API-nya.

        
Sourcify adalah verifier independen yang tidak membutuhkan API key. Ia berguna sebagai pembanding dan untuk kontrak yang ingin diverifikasi di luar Etherscan. Foundry bisa memakai Sourcify langsung.

        

          
Verifikasi Sourcify

          
forge verify-contract \
  0xALAMAT_KONTRAK \
  src/MiniVault.sol:MiniVault \
  --chain sepolia \
  --verifier sourcify \
  --watch

        

        
Verifikasi di dua tempat tidak saling menggantikan. Etherscan lebih sering dipakai pengguna, Sourcify memberi bukti tambahan. Untuk latihan, satu verifier sudah cukup. Untuk rilis publik, pertimbangkan keduanya.


        
Kalau verifikasi gagal

        
    
          
  1. Bandingkan compiler dan optimizer.
    Lihat pengaturan yang benar-benar dipakai saat deploy. Jangan menebak dari file konfigurasi yang mungkin sudah berubah.
    2. 
          
  2. Periksa constructor args.
    Urutan, tipe, dan nilai harus sama. Gunakan cast abi-encode, bukan string manual.
    3. 
          
  3. Periksa source yang diunggah.
    Pastikan file import dan versi OpenZeppelin sama. File yang "mirip" tidak cukup.
    4. 
          
  4. Periksa library dan viaIR.
    Library harus di-link di alamat yang sama. viaIR mengubah bytecode.
    5. 
          
  5. Gunakan standard JSON input.
    forge verify-contract --show-standard-json-input membantu membandingkan input yang dikirim dengan yang dipakai deploy.
    6. 
        

        

          Terverifikasi bukan berarti aman
          
Source yang cocok dengan bytecode bisa tetap memiliki bug, backdoor admin, atau fungsi mint tanpa batas. Verifikasi hanya menjawab "apakah bytecode ini berasal dari source ini". Ia tidak menjawab "apakah kontrak ini aman".

    • 
            
  • Membedakan read contract, write contract, dan event log.
    • 
            
  • Menemukan constructor args dan source yang terverifikasi.
    •

Membaca transaksi deploy

        
Pada transaksi deploy, To sering ditampilkan sebagai Contract Creation. Itu normal. Alamat kontrak baru muncul di receipt dan di bagian "Contract" pada halaman transaksi. Jangan mengira To kosong berarti transaksi gagal.

        
    
          
  • Status: Success atau Fail. Deploy yang revert akan Fail dan tetap memakai gas.
    • 
          
  • From: alamat deployer. Cocokkan dengan wallet development.
    • 
          
  • Value: ETH yang dikirim ke constructor. Biasanya 0.
    • 
          
  • Gas Limit dan Gas Used: batas dan pemakaian sebenarnya.
    • 
          
  • Transaction Fee: biaya aktual dalam ETH.
    • 
          
  • Input Data: creation bytecode dan constructor args. Bisa sangat panjang.
    • 
          
  • Logs: event dari constructor, misalnya kepemilikan.
    • 
        

        

          Input data bukan source
          
Input data berisi bytecode, bukan Solidity yang bisa dibaca. Untuk membaca source, buka tab Contract setelah verifikasi. Jangan menyalin input data ke chat dan berharap orang bisa menjelaskannya tanpa ABI.

        


        
Read Contract dan Write Contract

        
Tab Read Contract memanggil fungsi view atau pure lewat eth_call. Tidak ada transaksi, tidak ada gas, dan tidak perlu wallet terhubung. Tab Write Contract menyusun transaksi, meminta wallet menandatangani, dan membayar gas. Untuk fungsi payable, kamu bisa mengisi value.

        

          

            
Read Contract

            
    
              
  • owner(), totalDeposits(), balanceOf(address).
    • 
              
  • Gratis dan bisa dicoba siapa saja.
    • 
              
  • Tidak membuktikan wallet terhubung.
    • 
            

          

          

            
Write Contract

            
    
              
  • deposit(), withdraw(uint256), pause().
    • 
              
  • Membutuhkan wallet di Sepolia dan biaya gas.
    • 
              
  • Bisa gagal karena revert, saldo, atau hak akses.
    • 
            

          

        


        
Log dan event

        
Event berisi address, topics, dan data. Parameter indexed masuk ke topics dan bisa difilter. Parameter non-indexed ada di data. Explorer memakai ABI terverifikasi untuk menampilkan nama event dan argumen. Kalau kontrak belum terverifikasi, kamu hanya melihat topik heksadesimal.

        
Event bukan state. Ia catatan yang dipancarkan saat eksekusi. Membaca event berguna untuk riwayat dan indexer, tetapi jangan memakai event sebagai satu-satunya sumber kebenaran untuk saldo saat ini. Baca state kontrak untuk nilai terkini.


        
Internal transaction

        
Saat kontrak mengirim ETH ke alamat lain lewat call, transfer itu tidak muncul sebagai transaksi terpisah. Explorer menampilkannya sebagai internal transaction di dalam transaksi induk. Gas untuk call itu tetap bagian dari transaksi induk. Ini penting saat menghitung total transfer dan saat membaca kegagalan yang hanya terlihat di trace.


        
Jangan percaya semua label

        
Explorer punya label untuk token, kontrak, dan alamat yang dikirim pengguna. Label bisa menyesatkan. Token palsu bisa memakai nama dan simbol yang mirip. Source terverifikasi bisa berisi fungsi berbahaya. Alamat yang terlihat "resmi" belum tentu resmi. Selalu cocokkan alamat dengan sumber yang kamu percaya, bukan dengan nama token di explorer.

Aplikasi yang terhubung ke Sepolia harus tahu chain ID, RPC, alamat kontrak, dan ABI.   • Mendeteksi chain wallet yang salah dan meminta switch.
    •

    •

Config Wagmi untuk Sepolia

        
Contoh memakai Wagmi 2 dan Viem 2. Kalau kamu memasang versi mayor yang lebih baru, periksa panduan migrasinya. Nama hook dan opsi transport bisa berubah.

        

          
lib/wagmi.ts

          
import { createConfig, http } from "wagmi";
import { sepolia } from "wagmi/chains";
import { injected } from "wagmi/connectors";

const rpcUrl =
  process.env.NEXT_PUBLIC_SEPOLIA_RPC_URL ??
  "https://ethereum-sepolia-rpc.publicnode.com";

export const config = createConfig({
  chains: [sepolia],
  connectors: [injected()],
  transports: {
    [sepolia.id]: http(rpcUrl)
  },
  ssr: true
});

        

        
Kalau NEXT_PUBLIC_SEPOLIA_RPC_URL berisi API key berkuota, key itu akan terlihat di browser. Untuk aplikasi publik, pakai endpoint yang memang untuk klien, key yang dibatasi domain, atau proxy server. Jangan menaruh key rahasia di variabel publik hanya karena lebih mudah.


        
Mendeteksi chain yang salah

        
Wallet bisa berada di mainnet saat aplikasi mengharapkan Sepolia. Jangan mengirim transaksi dan berharap wallet memilih chain yang benar. Bandingkan useChainId() dengan chain target, tampilkan peringatan, dan sediakan tombol switch.

        

          
components/network-guard.tsx

          
"use client";

import { sepolia } from "wagmi/chains";
import { useChainId, useSwitchChain } from "wagmi";

export function NetworkGuard() {
  const chainId = useChainId();
  const { switchChain, isPending } = useSwitchChain();

  if (chainId === sepolia.id) return null;

  return (
    <div role="alert" className="warn">
      <p>Wallet berada di chain {chainId}. Aplikasi ini hanya mendukung Sepolia.</p>
      <button
        type="button"
        disabled={isPending}
        onClick={() => switchChain({ chainId: sepolia.id })}
      >
        {isPending ? "Menunggu wallet..." : "Pindah ke Sepolia"}
      </button>
    </div>
  );
}

        

        
Kalau wallet belum mengenal Sepolia, pengguna mungkin perlu menambahkan chain. Viem menyediakan aksi addChain pada wallet client. Jangan memaksa; tampilkan instruksi dan tangani penolakan sebagai keadaan normal.

Bab 16PRAKTIK

          
ABI adalah kontrak antara frontend dan bytecode.

          
Frontend tidak mengirim nama fungsi sebagai teks. Ia meng-encode selector dan argumen menjadi calldata, lalu mengirimkannya ke alamat kontrak. ABI memberi tahu encoder urutan dan tipe yang benar. Tanpa ABI yang cocok, tombol terlihat benar tetapi panggilannya salah.

          
    
            
  • Membaca fungsi view dengan ABI, alamat, dan argumen bertipe.
    • 
            
  • Menulis transaksi, menyimulasikan, dan menunggu receipt.
    • 
            
  • Membedakan read dan write dari sisi gas dan tanda tangan.
    • 
            
  • Memperbarui UI setelah transaksi berhasil.
    • 
          

        


        
Membaca kontrak

        
Fungsi view dan pure tidak mengubah state. Panggilan dilakukan lewat eth_call, tidak membutuhkan wallet, dan tidak memakai gas. Hasilnya dikembalikan sebagai data yang di-decode sesuai ABI.

        

          
Membaca MiniVault

          
"use client";

import { useAccount, useReadContract } from "wagmi";
import { formatEther } from "viem";
import { miniVaultAbi } from "@/contracts/mini-vault.abi";
import { getMiniVault } from "@/contracts/addresses";

export function VaultSummary() {
  const { address, chainId } = useAccount();
  const vault = chainId ? getMiniVault(chainId) : undefined;

  const { data: total, refetch } = useReadContract({
    address: vault,
    abi: miniVaultAbi,
    functionName: "totalDeposits",
    query: { enabled: Boolean(vault) }
  });

  const { data: saldo } = useReadContract({
    address: vault,
    abi: miniVaultAbi,
    functionName: "balanceOf",
    args: address ? [address] : undefined,
    query: { enabled: Boolean(vault && address) }
  });

  if (!vault) return <p>Chain belum didukung.</p>;
  return (
    <div>
      <p>Total deposit: {total ? formatEther(total) : "..."} ETH</p>
      <p>Saldo kamu: {saldo ? formatEther(saldo) : "..."} ETH</p>
      <button type="button" onClick={() => refetch()}>Muat ulang</button>
    </div>
  );
}

        

        
query.enabled mencegah panggilan saat alamat atau wallet belum siap. Tanpa itu, hook bisa mengirim request dengan argumen undefined dan menghasilkan error yang membingungkan.


        
Menulis kontrak

        
Fungsi yang mengubah state membutuhkan transaksi. Alurnya: simulasikan untuk menangkap revert lebih awal, minta wallet menandatangani, kirim, lalu tunggu receipt. Jangan menganggap hash berarti sukses.

        

          
Deposit ke MiniVault

          
"use client";

import { parseEther } from "viem";
import {
  useAccount,
  useSimulateContract,
  useWriteContract,
  useWaitForTransactionReceipt
} from "wagmi";
import { miniVaultAbi } from "@/contracts/mini-vault.abi";
import { getMiniVault } from "@/contracts/addresses";

export function DepositForm({ amount }: { amount: string }) {
  const { chainId } = useAccount();
  const vault = chainId ? getMiniVault(chainId) : undefined;
  const value = parseEther(amount || "0");

  const { data: simulation, error: simError } = useSimulateContract({
    address: vault,
    abi: miniVaultAbi,
    functionName: "deposit",
    value,
    query: { enabled: Boolean(vault && value > 0n) }
  });

  const { writeContract, data: hash, isPending, error } = useWriteContract();
  const { data: receipt, isLoading: confirming } =
    useWaitForTransactionReceipt({ hash });

  return (
    <div>
      <button
        type="button"
        disabled={!simulation || isPending || confirming}
        onClick={() => simulation && writeContract(simulation.request)}
      >
        {isPending ? "Konfirmasi di wallet..." : confirming ? "Menunggu blok..." : "Deposit"}
      </button>
      {simError && <p role="alert">Simulasi gagal: {simError.message}</p>}
      {error && <p role="alert">Transaksi gagal dikirim: {error.message}</p>}
      {receipt && <p>Status: {receipt.status}</p>}
    </div>
  );
}

        

        
Simulasi memakai state terbaru. Kalau state berubah setelah simulasi, transaksi tetap bisa revert. Karena itu, tetap tangani receipt status reverted dan tampilkan pesan yang bisa dipahami.


        
Calldata dan selector

        
Empat byte pertama calldata adalah selector fungsi, yaitu empat byte pertama hash Keccak-256 dari signature. Argumen di-encode setelahnya, masing-masing 32 byte untuk tipe statis. Kamu tidak perlu menghitung ini manual, tetapi membacanya membantu saat debug.

        

          
Calldata dengan Cast

          
cast calldata "deposit()"
# 0xd0e30db0

cast calldata "withdraw(uint256)" 10000000000000000
# 0x2e1a7d4d + argumen 32 byte

cast calldata "balanceOf(address)" 0x2222222222222222222222222222222222222222
# 0x70a08231 + alamat yang di-pad

        

        
Kalau calldata di explorer tidak cocok dengan fungsi yang kamu harapkan, periksa ABI dan urutan argumen. Address harus di-pad ke 32 byte, bukan dikirim sebagai string 42 karakter.


        
Memperbarui UI setelah sukses

        
Setelah receipt sukses, data lama masih ada di cache. Panggil refetch pada query yang relevan, atau invalidasi query key. Kalau memakai event, jangan mengandalkan event sebagai satu-satunya pembaruan; event bisa terlambat atau terlewat saat koneksi putus.

import { BaseError, ContractFunctionRevertedError } from "viem";

export function friendlyError(error: unknown) {
  if (error instanceof BaseError) {
    const revert = error.walk(
      (e) => e instanceof ContractFunctionRevertedError
    );
    if (revert) {
      return "Kontrak menolak transaksi: " + (revert.reason ?? "aturan tidak terpenuhi");
    }
    return error.shortMessage;
  }
  return "Terjadi kesalahan. Coba lagi.";
}
