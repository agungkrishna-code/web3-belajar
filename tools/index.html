    ERC-20, ERC-721, access control, pausable, dan reentrancy guard yang sudah diaudit. Pakai sebagai dependency bertag, bukan salinan lepas dari internet.

Bab 01FONDASI

Toolchain adalah rangkaian, bukan satu aplikasi.

Menulis kontrak hanya satu bagian kecil. Sebelum kontrak sampai ke jaringan, ia harus dikompilasi, diuji, di-deploy, dipanggil, dan diperiksa. Setiap langkah punya alat dan jenis kegagalan sendiri.

  • Memetakan lima pekerjaan dalam siklus hidup kontrak.
  • Membedakan compiler, test runner, node lokal, CLI, dan script.
  • Menjelaskan peran forge, cast, anvil, chisel, Remix, dan OpenZeppelin.
  • Mengenali langkah mana yang mencegah bug paling mahal.

Lima pekerjaan, bukan satu

Pemula sering menyebut semuanya "deploy". Padahal satu kontrak melewati beberapa pekerjaan yang berbeda. Compiler mengubah source menjadi bytecode dan ABI. Test runner menjalankan fungsi di EVM sementara. Node lokal menyediakan chain untuk dicoba. Script menyusun transaksi deploy. CLI membaca dan menulis ke chain setelah kontrak hidup.

Foundry membungkus pekerjaan itu dalam empat binary. Kamu tidak harus menghafal semuanya hari ini, tetapi kamu harus tahu binary mana yang menjawab pertanyaanmu.

Empat binary Foundry dan pekerjaan utamanya.

Remix menggabungkan editor, compiler, VM, dan debugger dalam browser. OpenZeppelin bukan framework, melainkan library kontrak yang kamu impor ke proyek. Keduanya melengkapi Foundry, bukan saling menggantikan.

Test adalah gerbang, bukan formalitas. Script yang sama bisa dijalankan dalam mode simulasi atau broadcast, sehingga kamu bisa melihat transaksi yang akan dikirim sebelum menandatanganinya.

Kenapa test ditulis dalam Solidity

Test Foundry adalah kontrak Solidity yang mewarisi forge-std/Test.sol. Artinya kamu memakai bahasa yang sama dengan kontrak, bisa memanggil fungsi internal, dan tidak perlu berpindah konteks ke JavaScript. Ini mempercepat iterasi, tetapi juga berarti test bisa melakukan hal yang tidak bisa dilakukan transaksi biasa lewat cheatcode.

Test tidak membuktikan kontrak bebas bug. Test membuktikan bahwa perilaku tertentu yang kamu pikirkan sudah diperiksa. Fuzz test memperluas jangkauan input. Invariant test memperluas jangkauan urutan panggilan. Audit manusia tetap diperlukan untuk asumsi yang tidak kamu sadari.

Siklus kerja minimum
# 1. compile
forge build

# 2. test cepat
forge test

# 3. trace saat gagal
forge test -vvv

# 4. node lokal di terminal lain
anvil

forge script script/Deploy.s.sol --rpc-url http://127.0.0.1:8545 --broadcast

# 6. panggil kontrak
cast call $ALAMAT "count()(uint256)" --rpc-url http://127.0.0.1:8545

Yang tidak diselesaikan tool

  • Desain yang salah. Compiler tidak tahu bahwa kamu memberi izin kepada alamat yang salah.
  • Test yang lemah. Coverage tinggi bisa berasal dari test yang tidak pernah memeriksa hasil.
  • Private key yang bocor. Foundry mempercepat deploy, termasuk deploy oleh orang yang menemukan key-mu.
  • Perubahan lingkungan. Test lokal lulus, tetapi RPC testnet lambat, nonce bentrok, atau gas limit berbeda.
  • Asumsi ekonomi. Harga, likuiditas, dan perilaku pengguna tidak muncul di trace.

Satu installer, empat binary

Bab 03FONDASI

Struktur proyek adalah dokumentasi pertama.

Sebelum membaca satu baris test, orang lain melihat susunan folder dan foundry.toml. Struktur yang jelas memisahkan kode produksi, test, script deploy, dan dependency.

  • Membaca peran src, test, script, lib, out, dan cache.
  • Menulis foundry.toml yang eksplisit tanpa menyalin semua opsi.
  • Memakai profil untuk pengembangan dan CI.
  • Menjaga secret dan dependency tetap terkendali.

Peta folder

proyek-latihan/ |-- foundry.toml konfigurasi proyek |-- remappings.txt opsional, memetakan import |-- .env secret lokal, jangan di-commit |-- src/ | |-- Counter.sol kode produksi | `-- MiniVault.sol |-- test/ | |-- Counter.t.sol unit test | |-- Counter.fuzz.t.sol fuzz test, pemisahan opsional | `-- MiniVault.invariant.t.sol |-- script/ | `-- Deploy.s.sol script deploy dan interaksi |-- lib/ | |-- forge-std/ library test dan cheatcode | `-- openzeppelin-contracts/ |-- out/ artifact build, biasanya di-ignore |-- cache/ cache compiler, biasanya di-ignore |-- broadcast/ catatan transaksi broadcast, sering di-commit `-- .gas-snapshot snapshot gas, di-commit bila dipakai

src/ berisi kode yang akan dikirim ke chain. test/ berisi kontrak test yang tidak pernah di-deploy ke produksi. script/ berisi kontrak script yang menyusun transaksi. lib/ berisi dependency, biasanya sebagai git submodule. Folder out/ dan cache/ bisa dibuat ulang, jadi jangan bergantung padanya sebagai satu-satunya salinan.

foundry.toml yang bisa dibaca

Konfigurasi minimal lebih baik daripada konfigurasi yang tidak dipahami. Mulai dari path, versi compiler, optimizer, dan pengaturan test. Tambahkan opsi lain saat ada alasan.

foundry.toml
[profile.default]
src = "src"
test = "test"
script = "script"
out = "out"
libs = ["lib"]
solc = "0.8.24"
optimizer = true
optimizer_runs = 200
evm_version = "cancun"
fs_permissions = [{ access = "read", path = "./" }]

[fuzz]
runs = 1000
max_test_rejects = 65536
seed = "0x1234"

[invariant]
runs = 256
depth = 50
fail_on_revert = false

[rpc_endpoints]
sepolia = "${SEPOLIA_RPC_URL}"
localhost = "http://127.0.0.1:8545"

[profile.ci.fuzz]
runs = 10000

[profile.ci.invariant]
runs = 1000
depth = 100

Bagian [profile.default] dipakai setiap kali kamu menjalankan forge. [fuzz] dan [invariant] mengatur kampanye test. [rpc_endpoints] memberi nama pada RPC agar perintah tidak penuh URL panjang. Bagian [profile.ci.*] hanya aktif bila kamu menjalankan FOUNDRY_PROFILE=ci.

Profil, secret, dan dependency

Profil memungkinkan satu proyek punya pengaturan berbeda untuk lokal dan CI. Jangan menaikkan jumlah fuzz run di profil default jika test menjadi lambat; letakkan kampanye berat di profil CI. Untuk secret, simpan di .env yang di-ignore, atau lebih baik di keystore dan environment milik CI. Jangan pernah menulis private key di foundry.toml.

Dependency Foundry biasanya berupa git submodule. Pin versi saat memasang, catat di README, dan periksa forge remappings setelah menambah library. Jalankan forge tree untuk melihat siapa mengimpor apa.

function test_WithdrawSetelahDeadline() public {
    uint256 deadline = vault.deadline();

    // tepat sebelum deadline: masih boleh
    vm.warp(deadline - 1);
    vm.prank(alice);
    vault.withdraw();

    // sesudah deadline: harus revert
    vm.warp(deadline + 1);
    vm.prank(alice);
    vm.expectRevert(Vault.Terlambat.selector);
    vault.withdraw();
}

Bab 10TESTING

          
Fuzzer mencari input yang tidak kamu pikirkan.

          
Unit test memeriksa contoh yang kamu pilih. Fuzz test memberi ribuan contoh dan membiarkan mesin mencari yang mematahkan assertion. Saat gagal, input itu di-shrink menjadi versi terkecil yang masih gagal.

          
    
            
  • Menulis testFuzz_ dan memahami siklus input.
    • 
            
  • Membatasi input dengan bound dan vm.assume.
    • 
            
  • Mengatur runs, seed, dan reject limit.
    • 
            
  • Mereproduksi kegagalan dan menyimpan corpus.

Cara kerja fuzz test

        
Fungsi test yang menerima parameter dianggap fuzz test. Foundry menghasilkan nilai acak untuk parameter itu, menjalankan test, lalu mengulang. Secara default ia menjalankan 256 run. Kalau satu input gagal, Foundry mencoba mengecilkan input tersebut agar kamu mendapat contoh minimal, lalu menampilkan seed dan input yang gagal.


        

          
test/Vault.t.sol

          
function testFuzz_Deposit(uint256 jumlah) public {
    // batasi ke rentang yang masuk akal
    jumlah = bound(jumlah, 0.01 ether, 100 ether);

    vm.deal(alice, jumlah);
    vm.prank(alice);
    vault.deposit{value: jumlah}();

    assertEq(vault.balanceOf(alice), jumlah);
    assertEq(vault.totalDeposits(), jumlah);
}

        


        
Parameter bisa lebih dari satu. Setiap parameter mendapat input acak. Kalau kamu memakai dua parameter yang saling bergantung, misalnya amount dan saldo, batasi keduanya dengan urutan yang jelas agar tidak menghasilkan kombinasi mustahil.


        
Bound atau assume?

        

          

            Dua cara membatasi input, dengan konsekuensi berbeda.
            
              
PendekatanCara kerjaKapan dipakai

            
            
              
bound(x, min, max)Memetakan nilai ke rentang, tidak membuang inputPaling sering. Input selalu valid dan setiap run terpakai.

              
vm.assume(kondisi)Membuang input yang tidak memenuhi kondisiUntuk kondisi yang sulit dipetakan, misalnya dua alamat harus berbeda.

              
Tanpa batasFuzzer bebas memilih seluruh ruang tipeUntuk menguji ketahanan terhadap input ekstrem.

            
          

        


        
Terlalu banyak assume membuat fuzzer membuang sebagian besar input. Foundry punya batas reject; setelah itu test dianggap gagal karena tidak menemukan input valid. Kalau kamu melihat reject tinggi, ganti ke bound atau perbaiki logika asumsi.

    Bab 11TESTING
    
          
    Invariant adalah janji yang harus bertahan setelah urutan apa pun.
    
          
    Unit test bertanya "apakah fungsi ini benar?". Invariant test bertanya "apakah hubungan antar state tetap benar setelah seratus panggilan acak?". Pertanyaan kedua menemukan bug yang tidak muncul di satu transaksi.
    
          
      
            
    • Membedakan example test, fuzz test, dan invariant test.
      • 
            
    • Memilih properti yang benar-benar harus selalu benar.
      • 
            
    • Menulis handler dan ghost variable.
      • 
            
    • Membaca urutan panggilan yang mematahkan invariant.
      • 
          
    
        
    

        
    Tiga lapis pengujian
    
        
    
          
    
            Setiap lapis menjawab pertanyaan berbeda. Kamu membutuhkan ketiganya.
            
              
    LapisPertanyaanContoh
    
                
            
              
    UnitApakah satu aksi menghasilkan state yang benar?Deposit 1 ETH menambah saldo 1 ETH.
    
              
    FuzzApakah aksi itu benar untuk banyak nilai?Deposit nilai apa pun dalam rentang menambah saldo sesuai nilai.
    
              
    InvariantApakah hubungan antar state bertahan setelah banyak aksi?Saldo kontrak selalu cukup untuk semua kewajiban.
    
                
          
    
        
    

        
    Properti, bukan skenario
    
        
    Invariant yang baik berbentuk hubungan yang tidak boleh dilanggar. Untuk vault, contohnya: saldo ETH kontrak harus selalu lebih besar atau sama dengan total kewajiban ke pengguna. Untuk token, total supply harus sama dengan jumlah saldo semua holder. Untuk sistem suara, jumlah suara tidak boleh melebihi jumlah pemilih terdaftar.
    
        
    Hindari invariant yang mengulang implementasi. assertEq(totalDeposits(), jumlahSemuaSaldo()) berguna, tetapi jika keduanya diubah di baris yang sama, test mungkin hanya mengulang kode. Pilih properti yang berasal dari aturan bisnis.

    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Test} from "forge-std/Test.sol";
import {MiniVault} from "../../src/MiniVault.sol";

contract VaultHandler is Test {
    MiniVault public vault;
    uint256 public ghost_depositSum;
    uint256 public ghost_withdrawSum;

    address[] public actors;
    address internal currentActor;

    constructor(MiniVault _vault) {
        vault = _vault;
        for (uint256 i = 0; i < 4; i++) {
            address aktor = makeAddr(string(abi.encodePacked("aktor", i)));
            actors.push(aktor);
            vm.deal(aktor, 100 ether);
        }
    }

    modifier useActor(uint256 seed) {
        currentActor = actors[bound(seed, 0, actors.length - 1)];
        vm.startPrank(currentActor);
        _;
        vm.stopPrank();
    }

    function deposit(uint256 amount, uint256 seed) external useActor(seed) {
        amount = bound(amount, 0.01 ether, 5 ether);
        vault.deposit{value: amount}();
        ghost_depositSum += amount;
    }

    function withdraw(uint256 amount, uint256 seed) external useActor(seed) {
        uint256 saldo = vault.balanceOf(currentActor);
        if (saldo == 0) return;

        amount = bound(amount, 1, saldo);
        vault.withdraw(amount);
        ghost_withdrawSum += amount;
    }
}

Jalankan forge build lagi setelah coverage jika langkah berikutnya membutuhkan artifact produksi.

    Bab 13TIM
    
          
    CI adalah tempat kebiasaan diuji ulang oleh mesin.
    
          
    Di laptop, kamu bisa melewatkan test karena buru-buru. Di CI, aturan yang sama berlaku untuk semua orang. Pipeline yang baik cepat memberi umpan balik dan tidak menyimpan rahasia di tempat yang salah.
    
          
      
            
    • Menjalankan build, test, dan fmt di GitHub Actions.
      • 
            
    • Memakai profil CI untuk kampanye yang lebih berat.
      • 
            
    • Mengelola secret dan deploy dengan aman.
      • 
            
    • Membedakan gate wajib dan sinyal opsional.
      • 
          
    
        
    

        
    Workflow minimum
    
        
    Workflow berikut memakai action resmi Foundry. Checkout harus mengambil submodule, karena dependency seperti forge-std dan OpenZeppelin biasanya berada di lib/ sebagai submodule.
    

        
    
          
    .github/workflows/contracts.yml
    
          
    name: contracts

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

concurrency:
  group: contracts-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          submodules: recursive

      - name: Foundry
        uses: foundry-rs/foundry-toolchain@v1
        with:
          version: stable

      - name: Format
        run: forge fmt --check

      - name: Build
        run: forge build --sizes

      - name: Test
        run: forge test -vvv
        env:
          FOUNDRY_PROFILE: ci

      - name: Coverage
        run: forge coverage --report summary
    
        
    

        
    Mulai dari workflow sesederhana ini. Jangan menambahkan cache, matrix, atau deploy sebelum build dan test stabil. Jika CI lambat, ukur dulu langkah mana yang mahal. Fuzz run yang tinggi dan fork test biasanya lebih mahal daripada compile.
    

        
    Profil CI
    
        
    Profil CI memungkinkan test lokal tetap cepat sementara CI menjalankan kampanye lebih luas. Contohnya 10.000 fuzz runs dan 1.000 invariant runs. Jangan menaruh angka itu di profil default jika kamu menjalankan test puluhan kali sehari.
    

        
    
          
    foundry.toml
    
          
    [profile.ci]
fuzz.runs = 10000
invariant.runs = 1000
invariant.depth = 100
    
        
    

        
    Sebutkan versi Foundry di README atau pin di action. Perbedaan versi bisa mengubah default fuzz, perilaku cheatcode, dan format output. Kalau CI memakai stable, build bisa berubah tanpa perubahan kode. Untuk proyek produksi, pertimbangkan pin versi dan perbarui secara terjadwal.
    

        
    Secret dan deploy
    
        
    Secret CI tidak boleh muncul di log. Jangan menulis private key di YAML, echo environment, atau artifact. Untuk testnet, gunakan akun khusus yang hanya berisi ETH uji. Untuk mainnet, gunakan multisig atau hardware wallet, dan jangan memberi pipeline akses tanpa persetujuan manusia.
    

        
    
          
    Deploy manual yang dijaga

    Di GitHub Actions, gunakan environment dengan required reviewers untuk job deploy. Simpan secret di environment tersebut, bukan di repository-wide secret. Untuk pull request dari fork, secret tidak tersedia; jangan merancang pipeline yang membutuhkannya untuk test dasar.
    

        
    Apa yang di-commit?
    
        
      
          
    • Ya: source, test, script, foundry.toml, remappings, lockfile atau submodule commit, .gas-snapshot bila dipakai, dan catatan broadcast deploy.
      • 
          
    • Tidak: .env, private key, keystore berisi dana nyata, out/, cache/, dan file yang bisa dibuat ulang.
      • 
          
    • Hati-hati: artifact ABI untuk frontend, file state Anvil, dan log RPC. Pastikan tidak mengandung data sensitif.
      • 
        
    

        
    
          CI hijau bukan audit
          
    Pipeline yang lulus berarti build dan test yang kamu tulis lulus. Ia tidak membuktikan tidak ada bug, tidak memeriksa desain ekonomi, dan tidak menggantikan review kode oleh manusia yang memahami domain.
    
        
    

        
    
          Inti bab
          
    CI menjaga agar aturan yang sama dijalankan setiap kali kode berubah. Mulai dari build, test, dan format. Tambahkan coverage dan gas sebagai sinyal. Lindungi secret dan deploy dengan persetujuan manusia.

    Bab 15DEPLOY
    
          
    Script deploy adalah kode, jadi perlakukan seperti kode.
    
          
    Forge script menyusun transaksi dalam Solidity. Kamu bisa mensimulasikan seluruh deploy sebelum mengirim apa pun, lalu mengulang dari langkah yang gagal tanpa mengulang transaksi yang sudah berhasil.
    
          
      
            
    • Menulis script dengan Script dan vm.startBroadcast.
      • 
            
    • Membedakan simulasi dan broadcast.
      • 
            
    • Memakai environment, rpc_endpoints, dan resume.
      • 
            
    • Membaca catatan transaksi di folder broadcast.
      • 
          
    
        
    

        
    Struktur script
    
        
    
          
    script/DeployMiniVault.s.sol
    
          
    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Script} from "forge-std/Script.sol";
import {console} from "forge-std/console.sol";
import {MiniVault} from "../src/MiniVault.sol";

contract DeployMiniVault is Script {
    function run() external returns (MiniVault vault) {
        vm.startBroadcast();

        vault = new MiniVault();

        vm.stopBroadcast();

        console.log("MiniVault:", address(vault));
        console.log("owner:", vault.owner());
    }
}
    
        
    

        
    Script mewarisi Script, file berakhiran .s.sol, dan fungsi utamanya run(). vm.startBroadcast() menandai bagian yang transaksinya harus dikirim. Tanpa --broadcast, Foundry hanya mensimulasikan dan tidak mengirim apa pun.
    

        
    
          msg.sender di dalam script
          
    Memulai broadcast mengubah pengirim transaksi yang keluar, bukan msg.sender di frame script saat itu. Jangan memakai msg.sender dari script sebagai alamat owner kecuali kamu paham betul konteksnya. Di contoh MiniVault, constructor memakai msg.sender di dalam constructor kontrak, sehingga owner adalah pengirim transaksi deploy.
    
        
    

        
    Simulasi dulu, broadcast kemudian
    
        
    
          
    Terminal

  --rpc-url localhost

# broadcast ke Anvil memakai akun yang tidak terkunci
forge script script/DeployMiniVault.s.sol:DeployMiniVault \
  --rpc-url localhost \

  --unlocked \
  --sender 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266

# broadcast ke testnet dengan keystore
forge script script/DeployMiniVault.s.sol:DeployMiniVault \
  --rpc-url sepolia \
  --account deployer \
  --broadcast
    
        
    

        
    Simulasi tetap membaca state jaringan. Ia bisa memberi tahu bahwa transaksi akan revert karena saldo kurang, nonce bentrok, atau izin tidak cukup. Simulasi bukan jaminan: state bisa berubah sebelum transaksi masuk, dan gas bisa berbeda.
    

        
    Resume, bukan ulang dari nol
    
        
    Kalau broadcast berhenti di tengah karena RPC putus atau transaksi gagal, jangan mengulang script dari awal. Foundry mencatat progres dan bisa melanjutkan dengan --resume. Ini mencegah deploy ganda dan menghemat waktu.
    

        
    
          
    Terminal
    
          
    forge script script/DeployMiniVault.s.sol:DeployMiniVault \
  --rpc-url sepolia \
  --account deployer \
  --broadcast \
  --resume
    
        
    

        
    Sejak Foundry 1.8.4, state resume disimpan dalam file .recovery.json versi tertentu. Jangan menghapus folder broadcast/ atau cache/ selama deploy belum selesai. Lanjutkan dengan versi Foundry yang sama atau lebih baru yang mendukung format tersebut.
    

        
    Membaca hasil deploy
    
        
    Foundry menulis catatan transaksi ke broadcast/. File run-latest.json berisi daftar transaksi, alamat kontrak, dan status. Script lain bisa membacanya dengan cheatcode file dan JSON. Ini berguna untuk deploy bertahap yang perlu mengetahui alamat kontrak sebelumnya.

    json,
    ".transactions[0].contractAddress"

Script yang baik memeriksa apakah kontrak sudah ada, apakah owner sudah benar, dan apakah konfigurasi awal sudah dijalankan. Untuk alat produksi, catat alamat di file konfigurasi atau registry, lalu validasi sebelum mengirim transaksi baru.

    Bab 18JARINGAN
    
          
    Fork test menguji kontrakmu di dunia yang sudah berisi orang lain.
    
          
    Di jaringan lokal kosong, semua kontrak kamu mulai dari nol. Di fork, kamu mewarisi state jaringan nyata: token, pool, oracle, dan akun besar. Ini cara menguji integrasi tanpa menyalin seluruh dunia.
    
          
      
            
    • Menjalankan test terhadap state jaringan nyata.
      • 
            
    • Memilih blok tetap agar hasil bisa direproduksi.
      • 
            
    • Memakai impersonate dan deal untuk akun besar.
      • 
            
    • Mengenali batas RPC, arsip, dan state yang berubah.
      • 
          
    
        
    

        
    Kapan fork test berguna
    
        
      
          
    • Kontrakmu berinteraksi dengan Uniswap, Aave, Chainlink, atau token yang sudah ada.
      • 
          
    • Kamu ingin mereproduksi bug yang terjadi pada blok tertentu.
      • 
          
    • Kamu menguji migrasi atau upgrade terhadap state produksi.
      • 
          
    • Kamu ingin memakai saldo akun besar tanpa benar-benar memilikinya.
      • 
        
    

        
    
          
    Terminal
    
          
    # fork pada blok terbaru
forge test --fork-url "$MAINNET_RPC_URL"

# pin blok agar hasil tidak berubah
forge test --fork-url "$MAINNET_RPC_URL" \
  --fork-block-number 21000000

forge test --match-test testFork --fork-url "$MAINNET_RPC_URL"
    
        
    

        
    Selalu pin blok untuk test yang masuk CI. Tanpa pin, state berubah setiap hari dan test bisa gagal atau lulus karena alasan yang tidak kamu ubah. Catat nomor blok di komentar test atau konfigurasi.

    Membuat fork di dalam test
    
        
    
          
    test/Fork.t.sol
    
          
    import {Test} from "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract ForkTest is Test {
    address internal constant WETH =
        0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2;

    function setUp() public {
        uint256 forkId = vm.createFork(
            vm.envString("MAINNET_RPC_URL"),
            21000000
        );
        vm.selectFork(forkId);
    }

    function testFork_BacaStateNyata() public view {
        uint256 total = IERC20(WETH).totalSupply();
        assertGt(total, 0);
    }

    function testFork_ImpersonateHolder() public {
        address holder = makeAddr("holder");

        // beri saldo WETH di fork, bukan di mainnet
        deal(WETH, holder, 1 ether);

        vm.prank(holder);
        IERC20(WETH).transfer(address(this), 1 ether);

        assertEq(IERC20(WETH).balanceOf(address(this)), 1 ether);
    }
}
    
        
    

        
    Untuk akun yang tidak punya private key, vm.prank cukup jika kamu hanya butuh msg.sender. Untuk memberi saldo ETH, gunakan vm.deal. Untuk memberi saldo token, forge-std menyediakan helper deal(address(token), recipient, amount). Ini mengubah state fork, bukan state jaringan asal.
    

        
    Batas dan jebakan
    
        
      
          
    • Bukan live. Perubahan di jaringan asal setelah blok fork tidak terlihat.
      • 
          
    • RPC bisa berubah. Provider bisa membatasi, memperlambat, atau menghapus cache.
      • 
          
    • Gas dan harga berbeda. Kondisi mempool dan base fee tidak direplikasi sempurna.
      • 
          
    • State besar. Fork test bisa lambat dan mahal secara kuota RPC.
      • 
          
    • Bukan audit. Integrasi yang lulus di satu blok belum tentu aman di semua kondisi.
      • 
        
    

        
    
          Inti bab
          
    Fork test memakai state nyata pada blok tertentu. Pin blok, jaga RPC tetap rahasia, dan gunakan impersonate atau deal untuk akun yang tidak kamu miliki. Fork adalah snapshot, bukan jaminan tentang masa depan.
    
        
    

        
    
          Latihan
          
    Buat fork test yang membaca totalSupply() dari token ERC-20 nyata di mainnet. Pin satu blok. Jelaskan mengapa test yang sama bisa berbeda hasilnya jika blok tidak dipin.
    
          
    
            Lihat jawaban
            
    Total supply bisa berubah karena mint atau burn. Tanpa pin, test membaca state terbaru setiap kali. Dengan pin, state dan hasilnya konsisten selama RPC menyediakan arsip blok tersebut.

    Debugging adalah membaca jejak, bukan menebak.

    src/MiniVault.sol
    
          
    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";
import {Pausable} from "@openzeppelin/contracts/utils/Pausable.sol";
import {ReentrancyGuard} from "@openzeppelin/contracts/utils/ReentrancyGuard.sol";

contract MiniVault is Ownable, Pausable, ReentrancyGuard {
    mapping(address => uint256) public balanceOf;
    uint256 public totalDeposits;

    error ZeroAmount();
    error InsufficientBalance();
    error TransferFailed();

    event Deposited(address indexed akun, uint256 jumlah);
    event Withdrawn(address indexed akun, uint256 jumlah);

    constructor() Ownable(msg.sender) {}

    receive() external payable {}

    function deposit() external payable whenNotPaused {
        if (msg.value == 0) revert ZeroAmount();

        balanceOf[msg.sender] += msg.value;
        totalDeposits += msg.value;

        emit Deposited(msg.sender, msg.value);
    }

    function withdraw(uint256 jumlah) external nonReentrant whenNotPaused {
        if (jumlah == 0) revert ZeroAmount();

        uint256 saldo = balanceOf[msg.sender];
        if (jumlah > saldo) revert InsufficientBalance();

        // effects sebelum interaction
        balanceOf[msg.sender] = saldo - jumlah;
        totalDeposits -= jumlah;

        (bool ok,) = msg.sender.call{value: jumlah}("");
        if (!ok) revert TransferFailed();

        emit Withdrawn(msg.sender, jumlah);
    }

    function pause() external onlyOwner {
        _pause();
    }

    function unpause() external onlyOwner {
        _unpause();
    }
}
    
        
    

        
    Mengapa kontrak ini disusun begini
    
        
      
          
    • CEI. Saldo dan total diperbarui sebelum ETH dikirim, sehingga penerima yang memanggil balik melihat state yang sudah benar.
      • 
          
    • nonReentrant. Guard menolak pemanggilan ulang selama eksekusi withdraw. CEI dan guard saling memperkuat.
      • 
          
    • whenNotPaused. Owner bisa menghentikan deposit dan withdraw saat ada insiden. Pause bukan pengganti audit.
      • 
          
    • Custom error. Lebih murah dan lebih jelas daripada string panjang.
      • 
          
    • receive. Donasi langsung menambah saldo kontrak tanpa menambah kewajiban. Karena itu invariant memakai >=.
      • 
          
    • Ownable(msg.sender). Deployer menjadi owner. Untuk produksi, pertimbangkan memindahkan ownership ke multisig atau timelock.
      • 
        
    

        
    
          Kekuatan owner
          
    pause() menghentikan deposit dan withdraw. Artinya owner bisa mencegah pengguna menarik dana. Ini tradeoff kepercayaan yang harus dijelaskan, bukan fitur netral. Untuk produksi, batasi owner dengan multisig atau timelock, dan siapkan prosedur unpause serta insiden.

    Glosarium
    
        
    
          
    ABI
    Deskripsi antarmuka kontrak: nama fungsi, tipe argumen, dan return. Dipakai cast, script, dan frontend untuk meng-encode panggilan.
    
          
    Anvil
    Node Ethereum lokal dari Foundry. Menyediakan akun berisi ETH, blok instan, state, dan fork.
    
          
    Artifact
    File JSON hasil build di folder out/. Berisi ABI, bytecode, metadata, dan kadang storage layout.
    
          
    Assertion
    Pernyataan yang harus benar di test, misalnya assertEq. Assertion bukan validasi produksi.
    
          
    Bound
    Fungsi forge-std untuk memetakan nilai acak ke rentang tertentu tanpa membuang input.
    
          
    Broadcast
    Mode forge script yang benar-benar mengirim transaksi. Tanpa flag ini, script hanya simulasi.
    
          
    Bytecode
    Kode mesin EVM hasil kompilasi. Runtime bytecode disimpan di akun kontrak.
    
          
    Cast
    Binary Foundry untuk membaca dan menulis ke chain dari terminal.
    
          
    Cheatcode
    Fungsi khusus test yang dipanggil lewat vm, misalnya prank, deal, warp, dan expectRevert.
    
          
    CI
    Continuous integration. Menjalankan build, test, dan pemeriksaan lain setiap kali kode berubah.
    
          
    Compiler
    Program yang mengubah Solidity menjadi bytecode dan ABI. Foundry mengelola versi lewat pragma atau konfigurasi.
    
          
    Corpus
    Kumpulan input atau urutan panggilan yang disimpan fuzzer untuk reproduksi dan pengujian berikutnya.
    
          
    Coverage
    Ukuran baris atau cabang yang dieksekusi test. Bukan ukuran kebenaran assertion.
    
          
    Custom error
    Error yang dideklarasikan dengan error Nama(...). Lebih murah dan terstruktur daripada string.
    
          
    Depth
    Jumlah panggilan dalam satu urutan invariant test.
    
          
    EIP-170
    Batas ukuran runtime code kontrak, sekitar 24.576 byte.
    
          
    Fork
    Salinan state jaringan pada blok tertentu. Perubahan di fork tidak memengaruhi jaringan asal.
    
          
    Foundry
    Toolchain smart contract berisi forge, cast, anvil, dan chisel.
    
          
    Fuzz test
    Test yang menerima input acak dan dijalankan berkali-kali untuk mencari nilai yang mematahkan assertion.
    
          
    Gas snapshot
    File catatan gas per test, dipakai untuk membandingkan perubahan biaya antar versi.
    
          
    Ghost variable
    Variabel di handler yang mencatat state tambahan, misalnya total deposit yang seharusnya.
    
          
    Handler
    Kontrak pembungkus di invariant test yang membatasi input dan memilih aktor.
    
          
    Invariant
    Properti yang harus selalu benar setelah urutan panggilan apa pun, misalnya solvensi vault.
    
          
    Keystore
    File terenkripsi berisi private key. Dipakai forge dan cast lewat opsi --account.
    
          
    Mutation test
    Mengubah source dengan mutan kecil lalu menjalankan test. Mutan yang survived menunjukkan test yang lemah.
    
          
    Nonce
    Penghitung transaksi per akun. Nonce yang salah membuat transaksi ditolak atau menggantikan transaksi lain.
    
          
    Optimizer
    Pengaturan compiler yang menukar ukuran kode dengan biaya eksekusi, atau sebaliknya.
    
          
    Prank
    Cheatcode yang membuat panggilan berikutnya terlihat berasal dari alamat tertentu.
    
          
    Remapping
    Aturan yang memetakan prefix import ke folder dependency, misalnya @openzeppelin/contracts/.
    
          
    Remix VM
    Chain simulasi di browser Remix, biasanya 10 akun dengan 100 ETH.
    
          
    Reentrancy
    Pemanggilan balik ke kontrak sebelum eksekusi pertama selesai. Dicegah dengan CEI dan guard.
    
          
    RPC
    Endpoint JSON-RPC yang menghubungkan alatmu ke node Ethereum.
    
          
    Seed
    Nilai yang mengatur urutan input fuzzer. Membantu reproduksi, tetapi bukan jaminan identik.
    
          
    Shrinking
    Proses mengecilkan input yang gagal menjadi versi minimal yang masih gagal.
    
          
    Simulation
    Menjalankan script atau panggilan terhadap state tanpa mengirim transaksi.
    
          
    Storage layout
    Peta slot dan offset variabel state. Penting untuk proxy dan upgrade.
    
          
    Test isolation
    Mode Foundry yang menjalankan panggilan eksternal test sebagai transaksi terpisah. Bisa dimatikan dengan --no-isolate.
    
          
    Trace
    Jejak call, gas, dan return atau revert selama eksekusi. Dibaca dengan -vvv atau debugger.
    
          
    Unit test
    Test yang memeriksa satu perilaku atau satu fungsi dengan state yang disiapkan.
    
          
    Via IR
    Pipeline compiler melalui intermediate representation. Kadang membantu stack too deep, tetapi mengubah output dan biaya.
