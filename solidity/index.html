Bab 01DASAR

Kontrak dan EVM.

Smart contract bukan file yang berjalan di servermu. Ia kode yang disimpan di sebuah akun blockchain, dan setiap node mengeksekusinya dengan aturan yang sama.

  • Membedakan akun milik pengguna dan akun kontrak.
  • Mengikuti perjalanan kode Solidity sampai menjadi state blockchain.
  • Memahami peran bytecode, ABI, storage, dan gas.
  • Menyebut hal yang tidak bisa dilakukan kontrak.

Dua jenis akun

Ethereum punya dua jenis akun. EOA (externally owned account) dikendalikan private key dan bisa memulai transaksi. Akun kontrak tidak punya private key. Ia hanya bisa bereaksi ketika dipanggil oleh EOA atau kontrak lain.

Akun kontrak tetap punya alamat dan saldo ETH. Yang membedakannya adalah adanya code yang dijalankan setiap kali ada panggilan masuk, serta storage miliknya sendiri yang persisten. Kontrak tidak bisa bangun sendiri, tidak bisa menjadwalkan transaksi, dan tidak bisa membaca email atau API tanpa bantuan pihak lain.

EOA

Private key, nonce, saldo. Bisa menandatangani dan mengirim transaksi. Contoh: akun MetaMask kamu.

Kontrak

Alamat, saldo, bytecode, storage. Tidak punya private key. Hanya jalan saat dipanggil dan membayar gas dari pemanggil.

Dari Solidity ke bytecode

Kamu menulis Solidity. Compiler solc mengubahnya menjadi dua hal yang berbeda: bytecode yang dieksekusi EVM, dan ABI yang menjelaskan cara memanggil fungsi dari luar. Bytecode disimpan di akun kontrak. ABI tidak disimpan on-chain; ia hanya kontrak antar muka untuk aplikasi, wallet, dan block explorer.

ABI dibagikan ke aplikasi lewat artifact. Bytecode disimpan di akun kontrak. Pemanggilan berikutnya tidak mengirim ulang kode, hanya selector fungsi dan argumen yang di-encode.

Apa yang terjadi saat deploy

  1. Transaksi dikirim ke alamat kosong

    Kamu mengirim transaksi dengan to kosong dan data berisi bytecode deploy. Biaya gas bergantung pada ukuran kode.

  2. Constructor berjalan sekali

    Constructor menyiapkan nilai awal, bisa membaca argumen, dan tidak pernah dijalankan lagi setelah deploy. Ini tempat yang tepat untuk immutable.

  3. Runtime code disimpan

    EVM menyimpan bagian kode yang akan dieksekusi pada panggilan berikutnya. Alamat kontrak dihitung dari alamat pengirim dan nonce, atau ditentukan lewat CREATE2.

  4. State awal disepakati

    Semua node menjalankan transaksi yang sama dan harus menghasilkan state yang sama. Kalau hasilnya berbeda, konsensus gagal. Karena itu kontrak tidak boleh bergantung pada data lokal yang tidak deterministik.

EVM: mesin tumpukan 256 bit

EVM adalah mesin virtual yang mengeksekusi opcode. Ia punya stack untuk perhitungan sementara, memory yang hilang setelah transaksi, dan storage yang persisten per kontrak. Setiap opcode punya harga gas. Menulis storage baru adalah salah satu operasi termahal karena data harus disimpan selamanya oleh setiap node.

Karena semua angka dasar adalah 256 bit, tipe uint256 adalah tipe native EVM. Tipe lebih kecil seperti uint8 menghemat storage bila dipaketkan, tetapi perhitungannya tetap memakai word 256 bit di belakang layar.

Penyimpanan.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Penyimpanan {
    uint256 public nilai;          // slot 0, persisten
    address public immutable pemilik; // bukan storage, disimpan di code

    event NilaiDiubah(uint256 nilaiBaru, address oleh);

    constructor() {
        pemilik = msg.sender;      // sekali, saat deploy
    }

    function ubah(uint256 baru) external {
        nilai = baru;              // menulis storage, bayar gas
        emit NilaiDiubah(baru, msg.sender);
    }

    function baca() external view returns (uint256) {
        return nilai;              // membaca storage, tidak mengubah state
    }
}

Perhatikan bahwa tidak ada fungsi main(). Kontrak tidak berjalan sendiri. Ia hanya mengeksekusi fungsi yang dipanggil, atau menerima ETH lewat receive dan fallback yang akan kamu pelajari di Bab 09.

Yang tidak bisa dilakukan kontrak

  • Menyimpan rahasia. Semua code dan storage publik. Nilai private hanya membatasi akses dari Solidity, bukan dari pembaca blockchain.
  • Mengambil data internet. Kontrak deterministik. Untuk harga, cuaca, atau hasil pertandingan, kamu butuh oracle.
  • Menghasilkan angka acak yang aman. block.timestamp dan block.prevrandao bisa dipengaruhi validator. Untuk lotre bernilai besar, pakai VRF.
  • Menjadwalkan dirinya sendiri. Tidak ada timer on-chain. Eksekusi berikutnya harus dipicu transaksi lain, keeper, atau otomasi.
  • Menghapus riwayat. delete mengosongkan storage saat ini, tetapi jejak transaksi lama tetap ada di chain dan arsip node.
  • Mengubah kode dirinya. Kode tidak bisa diganti. Upgrade dilakukan dengan pola proxy yang menunjuk ke kontrak implementasi baru.
Inti bab

Kontrak adalah akun dengan kode dan storage. Kode tidak berjalan sendiri, tidak menyimpan rahasia, dan tidak bisa mengakses dunia luar tanpa bantuan. Semua yang kamu desain harus deterministik dan bisa dibayar gas-nya.

Latihan

Sebuah kontrak menyimpan string private password = "rahasia". Apakah pengguna lain bisa membacanya? Jelaskan.

Bisa. private hanya mencegah kontrak lain mengakses variabel itu lewat Solidity. Storage tetap bisa dibaca langsung dari node dengan eth_getStorageAt atau lewat block explorer, karena semua state publik. Jangan pernah menyimpan password, API key, atau data pribadi on-chain.

Kontrak pertama dan test-nya

Simpan sebagai src/Counter.sol. Perhatikan bahwa kontrak ini sudah memakai empat konsep yang akan dibahas: state, event, custom error, dan modifier.

src/Counter.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
    uint256 public count;
    address public immutable owner;

    event CountChanged(uint256 indexed newCount, address indexed by);
    error NotOwner();

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner();
        _;
    }

    function increment() external {
        count += 1;
        emit CountChanged(count, msg.sender);
    }

    function decrement() external onlyOwner {
        require(count > 0, "Counter: sudah nol");
        count -= 1;
        emit CountChanged(count, msg.sender);
    }

    function reset() external onlyOwner {
        count = 0;
        emit CountChanged(0, msg.sender);
    }
}
test/Counter.t.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Test} from "forge-std/Test.sol";
import {Counter} from "../src/Counter.sol";

contract CounterTest is Test {
    Counter counter;
    address pengguna = address(0xBEEF);

    function setUp() public {
        counter = new Counter();
    }

    function testIncrement() public {
        counter.increment();
        assertEq(counter.count(), 1);
    }

    function testDecrementRevertSaatNol() public {
        vm.expectRevert("Counter: sudah nol");
        counter.decrement();
    }

    function testHanyaOwnerBisaReset() public {
        counter.increment();
        vm.prank(pengguna);
        vm.expectRevert(Counter.NotOwner.selector);
        counter.reset();
        assertEq(counter.count(), 1);
    }
}

Bab 03DASAR

Variabel dan tipe data.

Solidity tidak punya tipe number yang longgar. Setiap bit harus kamu pilih, karena ukuran tipe menentukan biaya, jangkauan, dan bug yang mungkin terjadi.

  • Membedakan value type dan reference type.
  • Memilih ukuran integer dan alamat dengan sadar.
  • Memakai satuan ETH dan waktu tanpa salah hitung.
  • Menghindari bug casting dan overflow.

Value type: disalin, bukan ditunjuk

Value type menyimpan nilainya langsung. Saat kamu menugaskan ke variabel lain, nilainya disalin. Perubahan pada salinan tidak memengaruhi aslinya.

Nilai default tidak pernah null. Variabel yang belum diisi bernilai nol: 0, false, address(0), atau string kosong. Karena itu, mapping tidak bisa membedakan "belum ada" dan "ada dengan nilai nol" tanpa penanda tambahan.

TipeDasar.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract TipeDasar {
    // value type
    bool public aktif = true;
    uint256 public total;              // default 0
    uint8 public kecil;                // 0..255
    int256 public suhu = -12;
    address public pemilik;
    bytes32 public hashData;

    // satuan
    uint256 public satuEther = 1 ether;        // 10**18 wei
    uint256 public satuGwei = 1 gwei;          // 10**9 wei
    uint256 public satuHari = 1 days;          // 86400 detik
    uint256 public satuMinggu = 1 weeks;       // 604800 detik

    // compile-time, tidak memakai slot storage
    uint256 public constant BATAS = 100;
    address public immutable deployer;

    constructor() {
        deployer = msg.sender;
        pemilik = msg.sender;
    }

    function contohCast() external pure returns (uint256, uint8, address) {
        uint256 besar = 300;
        uint8 kecilKan = uint8(besar);   // 300 % 256 = 44, terpotong!
        address nol = address(0);
        return (besar, kecilKan, nol);
    }
}

Reference type: menunjuk ke data

Reference type menyimpan data di tempat lain dan variabelnya menyimpan referensi atau offset. Yang termasuk di sini adalah array, bytes, string, struct, dan mapping. Perilaku penyalinan bergantung pada lokasi data: storage, memory, atau calldata, yang dibahas di Bab 07.

string sebenarnya adalah bytes yang diinterpretasikan sebagai UTF-8. Untuk data biner sembarang, pakai bytes. Untuk teks pendek yang jarang diubah, bytes32 bisa lebih murah, tetapi lebih repot dibaca.

Reference.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Reference {
    struct Profil {
        string nama;
        uint256 poin;
    }

    uint256[] public daftar;
    mapping(address => Profil) public profil;
    string public pesan = "halo";

    function tambah(uint256 nilai) external {
        daftar.push(nilai);
    }

    function setProfil(string calldata nama) external {
        profil[msg.sender] = Profil(nama, 0); // struct literal
    }

    function poinNaik() external {
        Profil storage p = profil[msg.sender]; // pointer, bukan salinan
        p.poin += 1;
    }
}

Memilih ukuran integer

Gunakan uint256 sebagai default. Ia native, tidak memerlukan konversi, dan paling aman untuk perhitungan umum. uint8 atau uint128 hanya menghemat storage kalau beberapa variabel kecil dideklarasikan berurutan sehingga bisa dipaketkan dalam satu slot 32 byte. Di dalam memori dan stack, EVM tetap memakai 256 bit, jadi tidak ada penghematan gas dari tipe kecil.

Sejak Solidity 0.8, overflow dan underflow pada integer checked dan otomatis revert. Kamu bisa mematikan pemeriksaan dengan unchecked hanya ketika kamu yakin secara matematis, misalnya pada pengurangan yang sudah dicek sebelumnya. Jangan memakai unchecked untuk mengejar gas sebelum ada bukti bahwa itu hotspot.

Satuan ETH dan waktu

Blockchain menyimpan nilai dalam wei. 1 ether adalah literal untuk 10**18 wei. Satuan waktu juga literal: 1 seconds, 1 minutes, 1 hours, 1 days, 1 weeks. Tidak ada bulan atau tahun karena panjangnya tidak tetap.

Jangan mengandalkan block.timestamp untuk presisi tinggi. Validator punya ruang geser beberapa detik. Untuk batas waktu yang longgar, timestamp cukup. Untuk lelang presisi milidetik, mekanisme on-chain murni adalah pilihan yang salah.

Perhitungan memakai string dan BigInt agar tidak kehilangan presisi. Contoh 0.1 + 0.2 pada floating point tidak sama dengan 0.3; di Solidity semua nilai integer, jadi tidak ada masalah itu, tetapi konversi desimal ke wei harus eksak.

Bug casting yang sering terjadi

Konversi ke tipe lebih kecil memotong bit atas tanpa peringatan. uint8(300) menghasilkan 44. Konversi uint256 ke int256 di atas type(int256).max akan revert pada 0.8. Sebaliknya, int256(-1) ke uint256 menjadi angka maksimum. Selalu periksa jangkauan sebelum cast, atau gunakan library seperti SafeCast dari OpenZeppelin.

Alamat juga punya jebakan. address(uint160(...)) memotong 20 byte terakhir. Jangan pernah mengubah angka menjadi alamat tanpa memahami asal angkanya. Alamat nol bukan alamat yang valid untuk menerima aset, dan banyak token akan revert atau membakar token jika dikirim ke sana.

Jangan simpan rahasia

Tipe private dan string tidak membuat data rahasia. Semua storage bisa dibaca dari node. Untuk data sensitif, simpan hash atau commitment on-chain, dan simpan isi aslinya off-chain.

Latihan

Lihat jawaban

Bab 04DASAR

Fungsi, visibility, dan mutability.

Fungsi adalah satu-satunya cara kontrak melakukan sesuatu. Siapa yang boleh memanggil, apa yang boleh diubah, dan siapa yang membayar, semuanya ditentukan di signature.

  • Menulis fungsi dengan parameter dan return yang jelas.
  • Memilih public, external, internal, atau private.
  • Membedakan view, pure, dan payable.
  • Memahami selector dan receive/fallback.

Anatomi fungsi

Fungsi.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Fungsi {
    mapping(address => uint256) public saldo;

    // nama fungsi, parameter, visibility, mutability, return
    function tambah(uint256 jumlah) external returns (uint256 saldoBaru) {
        saldoBaru = saldo[msg.sender] + jumlah;
        saldo[msg.sender] = saldoBaru;
    }

    // beberapa nilai kembali
    function info(address akun)
        external
        view
        returns (uint256 nilai, bool kosong)
    {
        nilai = saldo[akun];
        kosong = nilai == 0;
    }

    // fungsi internal, hanya dipakai di dalam kontrak atau turunannya
    function _kurangi(address akun, uint256 jumlah) internal {
        require(saldo[akun] >= jumlah, "saldo kurang");
        saldo[akun] -= jumlah;
    }

    // fungsi murni: tidak membaca state, tidak menulis state
    function tambahDua(uint256 x) external pure returns (uint256) {
        return x + 2;
    }
}

Nama parameter dan return boleh berbeda. Named return membuat variabel otomatis dideklarasikan; kamu bisa memakai return eksplisit atau membiarkan nilainya terisi di akhir fungsi. Untuk fungsi pendek, named return enak dibaca. Untuk logika panjang, return eksplisit lebih jelas.

Perbedaan public dan external lebih dari gaya. Fungsi external membaca argumen langsung dari calldata, sehingga lebih murah untuk array dan struct besar. public menyalin argumen ke memory. Sebaliknya, public bisa dipanggil dari dalam kontrak tanpa panggilan eksternal. Aturan praktis: pakai external untuk pintu masuk, internal untuk logika bersama, dan public hanya bila memang perlu dipanggil dari dalam dan luar.

Mutability: apa yang boleh dilakukan

  • view membaca state tetapi tidak mengubahnya. Pemanggilan dari luar gratis karena tidak perlu transaksi. Dari dalam transaksi, tetap memakai gas.
  • pure tidak membaca maupun mengubah state. Ia hanya memakai argumen dan konstanta. Ini janji terkuat dan paling mudah diuji.
  • payable boleh menerima ETH. Fungsi tanpa payable akan revert jika dikirim msg.value > 0.
  • nonpayable (default) tidak menerima ETH dan boleh mengubah state.

Compiler akan menolak fungsi view yang menulis storage, tetapi tidak bisa mendeteksi semua efek samping. view masih bisa memanggil kontrak lain yang membaca data berubah, jadi jangan menganggapnya sebagai jaminan determinisme mutlak.

Selector: empat byte pertama

Panggilan eksternal tidak menyebut nama fungsi. Yang dikirim adalah function selector, yaitu empat byte pertama dari keccak256("namaFungsi(tipeArgumen,...)"), diikuti argumen yang di-encode 32 byte per nilai.

// contoh calldata:
// 0xa9059cbb
// 0000000000000000000000001111...2222

Overloading membuat dua fungsi dengan nama sama dan tipe parameter berbeda. Selector-nya berbeda, tetapi overloading menyulitkan pembaca dan alat. Untuk kontrak baru, hindari overloading kecuali ada alasan kuat.

receive dan fallback

Dua fungsi khusus menangani panggilan yang tidak cocok dengan fungsi mana pun. receive() external payable dipanggil saat calldata kosong, termasuk transfer ETH tanpa data. fallback() external payable dipanggil untuk calldata yang tidak dikenal, atau saat tidak ada receive. Keduanya opsional. Kalau tidak ada dan kontrak menerima ETH tanpa data, transaksi revert.

Penerima.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Penerima {
    event Diterima(address indexed dari, uint256 jumlah);

    receive() external payable {
        emit Diterima(msg.sender, msg.value);
    }

    fallback() external payable {
        // dipanggil untuk calldata tak dikenal
        revert("fungsi tidak ada");
    }
}

Siapa boleh memanggil apa

Pemanggil

Pilih pemanggil, lalu salah satu fungsi.

Dari dalam kontrak, external hanya bisa dipanggil sebagai this.external(), yang berarti panggilan eksternal baru dan memakai gas tambahan. Itu bukan cara umum memanggil fungsi internal.

Fungsi sebagai tipe dan callback

Solidity mendukung function type, misalnya function(uint256) external returns (bool). Ini dipakai untuk mengirim callback ke kontrak lain, tetapi juga memperbesar permukaan serangan. Bab 05DASAR

Alur kontrol dan error handling.

Transaksi yang gagal bukan bencana. Yang berbahaya adalah transaksi yang berhasil padahal seharusnya gagal. Di Solidity, kamu menulis penjaga di setiap batas.

  • Memakai if, loop, dan break tanpa membuat gas meledak.
  • Membedakan require, revert, assert, dan custom error.
  • Memahami rollback dan biaya transaksi gagal.
  • Menangani kegagalan panggilan eksternal dengan try/catch.

Alur yang sederhana

Alur.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Alur {
    uint256[] public nilai;

    function contoh(uint256 x) external pure returns (string memory) {
        if (x == 0) {
            return "nol";
        } else if (x < 10) {
            return "kecil";
        }
        return x % 2 == 0 ? "genap" : "ganjil";
    }

    function jumlahkan(uint256 batas) external pure returns (uint256 total) {
        for (uint256 i = 0; i < batas; i++) {
            if (i > 1000) break;   // pengaman, bukan solusi
            total += i;
        }
    }

    function isi(uint256 n) external {
        for (uint256 i = 0; i < n; i++) {
            nilai.push(i);
        }
    }
}

Loop di Solidity boleh, tetapi setiap iterasi memakai gas. Loop yang panjangnya ditentukan pengguna bisa membuat fungsi tidak bisa dipanggil sama sekali. Ini disebut denial of service karena gas habis sebelum selesai. Untuk data besar, pindahkan perhitungan off-chain atau pecah menjadi beberapa transaksi.

Error.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Error {
    error SaldoKurang(uint256 diminta, uint256 tersedia);
    error SudahSelesai();

    mapping(address => uint256) public saldo;
    bool public selesai;

    function tarik(uint256 jumlah) external {
        uint256 tersedia = saldo[msg.sender];

        if (jumlah == 0) revert("jumlah nol");
        if (jumlah > tersedia) revert SaldoKurang(jumlah, tersedia);

        saldo[msg.sender] = tersedia - jumlah;
        // kirim ETH setelah state diperbarui (lihat Bab 09)
    }

    function tandaiSelesai() external {
        if (selesai) revert SudahSelesai();
        selesai = true;
    }
}

Custom error diperkenalkan di Solidity 0.8.4. Ia lebih murah daripada string karena tidak menyimpan pesan panjang, dan bisa membawa data terstruktur yang bisa dibaca frontend. Gunakan custom error untuk kontrak baru. String tetap berguna untuk pesan yang ingin dibaca manusia langsung di explorer, tetapi jangan memakai string panjang berulang-ulang.

Rollback: apa yang kembali dan apa yang tidak

Saat transaksi revert, semua perubahan state dalam transaksi itu dibatalkan, termasuk perubahan pada kontrak lain yang dipanggil. Log dan event juga dibatalkan. Yang tidak kembali adalah gas yang sudah terpakai dan biaya dasar transaksi. Jadi transaksi gagal tetap mengurangi saldo ETH pengirim.

Karena itu, validasi murah sebaiknya dilakukan paling awal. Jangan melakukan perhitungan berat atau menulis storage sebelum memastikan pemanggil berhak dan input masuk akal.

try/catch untuk panggilan eksternal

try/catch hanya bekerja pada panggilan eksternal, bukan pada internal call. Ia berguna ketika kamu memanggil kontrak lain dan ingin tetap melanjutkan walau panggilan itu gagal. Jangan memakainya untuk menyembunyikan kegagalan penting.

Coba.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface IOracle {
    function harga() external view returns (uint256);
}

contract Coba {
    event Gagal(string alasan);

    function bacaHarga(IOracle oracle) external returns (uint256 hasil) {
        try oracle.harga() returns (uint256 h) {
            return h;
        } catch Error(string memory alasan) {
            emit Gagal(alasan);
            return 0;
        } catch (bytes memory) {
            emit Gagal("gagal tanpa pesan");
            return 0;
        }
    }
}

    Bab 06DASAR

    Mapping dan struct.

    Mapping adalah laci tanpa daftar isi. Kamu bisa membuka laci dengan kunci yang tepat, tetapi tidak bisa bertanya "ada berapa laci" atau "tunjukkan semuanya" tanpa menyimpan daftarnya sendiri.

    • Menyimpan data berdasarkan key dengan mapping.
    • Membuat struktur data dengan struct dan array of struct.
    • Menjelaskan kenapa mapping tidak bisa diiterasi.
    • Menghapus data dan membedakan kosong dari nol.

    Mapping: key ke value

    Mapping dideklarasikan dengan tipe key dan tipe value. Key harus value type atau bytes/string; value bisa apa saja, termasuk mapping lain atau struct. Semua key yang belum pernah ditulis mengembalikan nilai default, bukan error.

    Tidak ada length, tidak ada iterasi, dan tidak ada cara menemukan key yang pernah dipakai. Mapping tidak menyimpan daftar key. Kalau kamu butuh enumerasi, simpan array key terpisah dan jaga konsistensinya sendiri.

    Mapping.sol
    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Mapping {
    mapping(address => uint256) public saldo;
    mapping(address => mapping(address => uint256)) public izin;
    mapping(uint256 => bool) public terdaftar;

    function isi(uint256 jumlah) external {
        saldo[msg.sender] += jumlah;
    }

    function setIzin(address pemakai, uint256 batas) external {
        izin[msg.sender][pemakai] = batas;
    }

    function cek(address pemilik, address pemakai)
        external
        view
        returns (uint256)
    {
        return izin[pemilik][pemakai]; // 0 kalau belum pernah diset
    }

    function hapus() external {
        delete saldo[msg.sender]; // mengembalikan ke nilai default
    }
}

    Mapping dengan tipe value uint256 bisa dibuat public. Compiler menghasilkan getter yang menerima key dan mengembalikan value. Getter otomatis ini tidak bisa dipakai untuk mapping bersarang dengan dua level sekaligus; kamu perlu fungsi eksplisit seperti cek di atas.

    Struct: mengelompokkan field

    Struct mendefinisikan tipe baru dengan beberapa field. Ia berguna saat data selalu bergerak bersama, misalnya profil pengguna, item, atau proposal. Struct bisa disimpan di storage, memory, atau calldata.

    Struct yang berisi field kecil bisa dipaketkan dalam storage, tetapi struct di memory selalu memakai slot 32 byte per field. Ini memengaruhi biaya dan cara kamu mendesain parameter fungsi.

    Struct.sol
    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract DataPengguna {
    struct Profil {
        string nama;
        uint64 poin;
        bool aktif;
    }

    mapping(address => Profil) public profil;
    address[] public pengguna;

    event ProfilDibuat(address indexed akun, string nama);

    function buat(string calldata nama) external {
        require(bytes(nama).length > 0, "nama kosong");
        require(bytes(profil[msg.sender].nama).length == 0, "sudah ada");

        profil[msg.sender] = Profil({nama: nama, poin: 0, aktif: true});
        pengguna.push(msg.sender);
        emit ProfilDibuat(msg.sender, nama);
    }

    function tambahPoin(address akun, uint64 jumlah) external {
        Profil storage p = profil[akun]; // pointer ke storage
        require(p.aktif, "tidak aktif");
        p.poin += jumlah;                // mengubah data asli
    }

    function nonaktifkan(address akun) external {
        profil[akun].aktif = false;
    }

    function jumlahPengguna() external view returns (uint256) {
        return pengguna.length; // daftar key disimpan manual
    }
}

    Perhatikan Profil storage p = profil[akun]. Kata storage membuat p menjadi referensi, bukan salinan. Mengubah p.poin mengubah storage kontrak. Kalau kamu menulis Profil memory p, kamu mendapat salinan dan perubahan itu hilang setelah fungsi selesai. Perbedaan ini dibahas lebih dalam di Bab 07.

    Array of struct dan penghapusan

    Untuk daftar yang perlu diiterasi, kamu bisa memakai Profil[] atau mapping(uint256 => Profil) plus array id. Yang kedua lebih umum karena id tetap stabil dan penghapusan tidak menggeser indeks.

    delete mengembalikan semua field ke nilai default. Untuk struct, setiap field direset. Untuk elemen array dinamis, delete arr[i] mengosongkan elemen tetapi tidak memperpendek array. Untuk menghapus dan memperpendek, tukar elemen terakhir ke posisi yang dihapus lalu pop(), atau pakai pola mapping plus id.

    HapusDenganTukar.sol
    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Daftar {
    uint256[] public nilai;

    function tambah(uint256 x) external {
        nilai.push(x);
    }

    // hapus indeks i tanpa meninggalkan lubang
    function hapus(uint256 i) external {
        require(i < nilai.length, "indeks salah");
        nilai[i] = nilai[nilai.length - 1];
        nilai.pop();
    }
}

    Pola tukar-lalu-pop mengubah urutan. Kalau urutan penting, jangan pakai pola ini. Kalau urutan tidak penting dan kamu ingin hemat gas, ini pilihan yang baik. Untuk daftar besar, iterasi tetap mahal; jangan menjadikan fungsi publik yang mengiterasi seluruh daftar sebagai satu-satunya cara membaca data.

        Storage, memory, dan calldata.

        Di JavaScript, objek adalah referensi dan kamu jarang memikirkan tempatnya. Di Solidity, tempat data menentukan apakah perubahan bertahan, berapa biayanya, dan apakah datanya bisa diubah.

        • Membedakan storage, memory, dan calldata.
        • Memahami kapan data disalin dan kapan direferensikan.
        • Membaca layout slot dan packing.
        • Mengurangi biaya gas dengan memilih lokasi yang tepat.

        Tiga lokasi data

        LokasiUmurBiayaBisa diubahDipakai untuk
        storageSelamanya, sampai dihapusPaling mahalYaState kontrak

        State variable selalu di storage. Parameter fungsi external bisa calldata atau memory. Parameter fungsi public dan internal harus memory. Variabel lokal yang mereferensikan storage harus diberi kata storage; tanpa itu, compiler akan menyalinnya ke memory untuk reference type.

        Referensi dan salinan

        LokasiData.sol
        // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract LokasiData {
    struct Akun {
        uint256 saldo;
        string nama;
    }

    mapping(address => Akun) public akun;

    // calldata: tidak disalin, hanya dibaca
    function setNamaCalldata(string calldata namaBaru) external {
        akun[msg.sender].nama = namaBaru;
    }

    // memory: disalin, aman diubah lokal
    function setNamaMemory(string memory namaBaru) external {
        akun[msg.sender].nama = namaBaru;
    }

    // storage pointer: mengubah data asli
    function tambahSaldo(uint256 jumlah) external {
        Akun storage a = akun[msg.sender];
        a.saldo += jumlah;
    }

    // memory copy: perubahan tidak bertahan
    function tambahSaldoSalah(uint256 jumlah) external {
        Akun memory a = akun[msg.sender];
        a.saldo += jumlah; // hilang setelah fungsi selesai
    }

    // parameter struct: calldata lebih murah untuk data besar
    function simpan(Akun calldata data) external {
        akun[msg.sender] = data;
    }
}

        Fungsi tambahSaldoSalah tidak mengubah state. Compiler tidak selalu memberi peringatan karena secara sintaks ia valid. Ini jenis bug yang harus kamu cari lewat test: panggil fungsi, lalu baca state dan pastikan nilainya berubah.

        Storage layout: slot 32 byte

        Storage kontrak adalah ruang virtual berisi slot 32 byte (256 bit), dimulai dari slot 0. State variable ditempatkan berurutan sesuai deklarasi. Beberapa variabel kecil bisa berbagi satu slot jika ukurannya cukup. Struct dan array selalu memulai slot baru; elemennya mengikuti aturan sendiri.

        Contoh deklarasi:

        Layout.sol
        // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Layout {
    uint128 public a;   // slot 0, byte 0..15
    uint128 public b;   // slot 0, byte 16..31
    address public c;   // slot 1, byte 0..19
    bool public d;      // slot 1, byte 20
    uint256 public e;   // slot 2 (tidak muat di slot 1)
    string public f;    // slot 3 (pointer ke data)
    uint256[] public g; // slot 4 (length; data di hash terpisah)
    mapping(address => uint256) public h; // slot 5 (basis hash)
}

        Untuk mapping, nilai pada key k berada di keccak256(abi.encode(k, slot)) untuk key value type. Key string dan bytes memakai data mentah tanpa padding, jadi rumusnya tidak sama. Untuk array dinamis, elemen ke-i berada di keccak256(abi.encode(slot)) + i, sedangkan panjangnya disimpan di slot deklarasi. Untuk string dan bytes, data pendek (31 byte atau kurang) disimpan langsung di slot dengan encoding panjang, sedangkan data panjang disimpan di lokasi hash terpisah.

        Kamu tidak perlu menghafal semua rumus, tetapi harus tahu bahwa mapping dan array tidak menyimpan elemen secara berurutan di slot deklarasinya. Ini menjelaskan kenapa delete pada array dinamis tidak otomatis membersihkan semua elemen, dan kenapa iterasi array besar bisa sangat mahal.

        Packing dan biaya

        Satu slot butuh biaya menulis yang jauh lebih besar daripada satu nilai di memori. Kalau kamu punya beberapa field kecil yang selalu dipakai bersama, deklarasikan berurutan agar bisa dipaketkan. Tetapi packing bukan tujuan utama. Membaca satu field dari slot yang dipakai bersama tetap memuat seluruh slot, dan menulis satu field bisa memaksa baca-ubah-tulis slot itu.

        Kalkulator packing storage

            Packing hanya berlaku untuk state variable yang berurutan dan cukup kecil. Struct, array, dan mapping memulai slot baru. Angka ini tidak menghitung biaya hash untuk mapping atau elemen array.

            Transient storage

            EIP-1153 menambahkan transient storage yang dibersihkan di akhir transaksi. Biayanya jauh lebih murah daripada storage persisten dan cocok untuk nilai sementara lintas panggilan, misalnya status reentrancy atau data flash loan. Dukungan compiler dan EVM harus dipastikan sebelum dipakai. Untuk sebagian besar kontrak, memory dan storage biasa sudah cukup.

            Modifier, event, dan inheritance.

            Tiga alat ini membuat kontrak bisa dipakai bersama: modifier menjaga pintu, event mencatat apa yang terjadi, dan inheritance menyusun perilaku dari bagian-bagian kecil.

            • Menulis modifier dan memahami urutan eksekusinya.
            • Menggunakan event untuk data yang perlu dibaca aplikasi.

            Modifier: penjaga sebelum dan sesudah

            Modifier adalah potongan kode yang dijalankan mengelilingi fungsi. Simbol _ menandai tempat badan fungsi disisipkan. Kode sebelum _ berjalan lebih dulu, kode sesudahnya berjalan setelah fungsi selesai.

            Modifier bisa menerima argumen dan bisa dirangkai. Urutan pemasangan penting: modifier yang ditulis lebih dulu dijalankan lebih luar, sehingga pre-check-nya berjalan lebih awal dan post-check-nya berjalan lebih akhir.

            Modifier.sol
            // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Terkunci {
    address public immutable owner;
    bool public paused;

    error NotOwner(address pemanggil);
    error ContractPaused();

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner(msg.sender);
        _;

        external
        onlyOwner
        whenNotPaused

    }

        paused = true;
    }

    function unpause() external onlyOwner {
        paused = false;
    }

}

            Jangan memakai modifier untuk logika yang perlu mengembalikan nilai atau yang terlalu panjang. Modifier yang rumit menyulitkan pembaca melacak alur. Untuk pengecekan sederhana, modifier mengurangi duplikasi. Untuk logika kompleks, panggil fungsi internal.

            Event: catatan untuk dunia luar

            Event dicatat dalam log transaksi. Kontrak tidak bisa membacanya kembali; event bukan storage. Aplikasi, indexer, dan block explorer membacanya dari receipt. Karena itu event jauh lebih murah daripada menyimpan riwayat di storage.

            Maksimal tiga parameter bisa diberi indexed pada event biasa. Parameter indexed bisa difilter oleh aplikasi, tetapi nilainya tidak bisa dibaca langsung dari data event tanpa log khusus. Parameter non-indexed disimpan di data dan lebih mudah dibaca utuh. String dan array indexed disimpan sebagai hash, bukan nilai aslinya.

            Inheritance: menyusun dari bagian kecil

            Satu kontrak bisa mewarisi beberapa kontrak. Fungsi dan state internal ikut diwarisi. Fungsi yang bisa ditimpa harus ditandai virtual di induk dan override di anak. super memanggil implementasi berikutnya dalam rantai pewarisan.

            Solidity memakai C3 linearization. Daftar is A, B, C ditulis dari yang paling dasar ke yang paling turunan: A paling dasar, C paling turunan. super bergerak dari kanan ke kiri dalam daftar, jadi ia mencoba C lebih dulu, lalu B, lalu A. Ini jarang menjadi masalah kalau hierarki dirancang dangkal, tetapi bisa membingungkan kalau terlalu dalam.

              Payable dan ETH.

              Menerima ETH mudah. Mengirimnya dengan aman jauh lebih sulit. Sebagian besar eksploitasi besar berawal dari satu baris yang mengirim ETH sebelum memperbarui state.

              • Menerima ETH lewat fungsi payable, receive, dan fallback.
              • Membedakan transfer, send, dan call.
              • Menerapkan checks-effects-interactions.
              • Mengenali reentrancy dan pola pull payment.

              Masuknya ETH ke kontrak

              Ada tiga pintu: fungsi payable, receive() external payable untuk panggilan tanpa data, dan fallback() external payable untuk calldata yang tidak dikenali. msg.value adalah jumlah wei yang dikirim bersama panggilan. Ia bisa dibaca di fungsi payable, tetapi tidak otomatis bertambah ke saldo kontrak secara eksplisit; saldo kontrak memang bertambah.

              Kontrak bisa menerima ETH tanpa fungsi payable jika dikirim lewat selfdestruct atau sebagai penerima fee validator. Jangan memakai address(this).balance sebagai satu-satunya sumber kebenaran akuntansi. Simpan total deposit sendiri.

              Reentrancy

              Reentrancy terjadi ketika kontrak mengirim ETH atau memanggil kontrak lain sebelum menyelesaikan pembaruan state. Penerima bisa memanggil balik fungsi yang sama sebelum saldo dikurangi, sehingga menarik dana berkali-kali. Pola checks-effects-interactions menutup celah ini: cek dulu, ubah state, baru berinteraksi.

        saldo[msg.sender] += msg.value;

    function tarik() external {

contract Aman {
    mapping(address => uint256) public saldo;
    bool private terkunci;

    error Reentrant();
    error TransferGagal();

    modifier nonReentrant() {
        if (terkunci) revert Reentrant();
        terkunci = true;
        _;
        terkunci = false;
    }

    function setor() external payable {
        saldo[msg.sender] += msg.value;
    }

    function tarik() external nonReentrant {
        uint256 jumlah = saldo[msg.sender];
        require(jumlah > 0, "kosong");

        saldo[msg.sender] = 0; // effects

        (bool ok, ) = payable(msg.sender).call{value: jumlah}("");
        if (!ok) revert TransferGagal();
    }
}

                  Keamanan kontrak.

                  Kontrak yang salah tidak bisa diperbaiki seperti aplikasi web. Bug adalah celah permanen yang bisa dilihat siapa saja, dan penyerang punya waktu tanpa batas.

                  • Menyebut sepuluh kelas kerentanan yang paling sering muncul.
                  • Menerapkan checks-effects-interactions dan akses berbasis role.
                  • Mengenali sumber data yang tidak bisa dipercaya.
                  • Menyusun checklist sebelum deploy.

                  Pola pikir: semua input tidak dipercaya

                  Setiap panggilan dari luar bisa datang dari siapa saja, pada waktu kapan saja, dengan data apa saja. Kontrak lain bisa berperilaku berbeda dari yang kamu kira, termasuk mengembalikan nilai palsu, memakai gas berlebihan, atau memanggil balik kontrakmu di tengah eksekusi. Jangan menganggap msg.sender ramah, dan jangan menganggap kontrak yang kamu panggil jujur.

                  Sepuluh kerentanan yang wajib dikenal

                  1. Reentrancy

                  Panggilan eksternal sebelum state selesai. Perbaiki dengan CEI, guard, dan pull payment.

                  2. Kontrol akses longgar

                  Fungsi penting tanpa modifier, atau tx.origin sebagai pengganti msg.sender.

                  3. Oracle yang bisa dimanipulasi

                  Harga dari satu pool tipis bisa digeser dalam satu transaksi. Pakai beberapa sumber, TWAP, dan cek staleness.

                  4. Randomness naif

                  block.timestamp, block.prevrandao, atau hash yang bisa diprediksi. Validator bisa memilih blok yang menguntungkan.

                  5. Overflow dan casting

                  0.8 memeriksa overflow, tetapi cast ke tipe kecil tetap memotong. Pakai SafeCast.

                  6. Signature replay

                  Tanda tangan tanpa nonce, chainId, atau domain bisa dipakai ulang. Gunakan EIP-712 dan nonce per akun.

                  7. Denial of service

                  Loop tak terbatas, push payment ke banyak penerima, atau array yang hanya bisa bertambah.

                  8. Delegatecall dan proxy

                  Delegatecall menjalankan kode asing di storage-mu. Proxy dengan layout salah bisa menimpa slot penting.

                  9. Front-running dan MEV

                  Transaksi terlihat di mempool. Untuk lelang dan slippage, desain mekanismenya sejak awal.

                  10. Kesalahan desain ekonomi

                  Kode benar, insentif salah. Contoh: hadiah lebih besar dari biaya serangan, atau harga awal bisa dimanipulasi.

                  Checks-effects-interactions

                  Urutan yang benar adalah: periksa semua kondisi, ubah state, baru lakukan panggilan eksternal. Kalau panggilan eksternal gagal dan kamu revert, seluruh perubahan state ikut dibatalkan. Kalau panggilan berhasil, state sudah konsisten.

                  CEI.sol
                  // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract ContohCEI {
    mapping(address => uint256) public saldo;
    uint256 public total;

    error JumlahNol();
    error SaldoKurang();
    error GagalKirim();

    function setor() external payable {
        if (msg.value == 0) revert JumlahNol();
        saldo[msg.sender] += msg.value;   // effect
        total += msg.value;               // effect
    }

    function tarik(uint256 jumlah) external {
        // 1. checks
        if (jumlah == 0) revert JumlahNol();
        uint256 tersedia = saldo[msg.sender];
        if (jumlah > tersedia) revert SaldoKurang();

        // 2. effects
        saldo[msg.sender] = tersedia - jumlah;
        total -= jumlah;

        // 3. interaction
        (bool ok, ) = payable(msg.sender).call{value: jumlah}("");
        if (!ok) revert GagalKirim();
    }
}

                  Akses: ownable, role, dan timelock

                  onlyOwner cukup untuk satu admin. Untuk tim, gunakan role terpisah: minter, pauser, treasury, upgrader. Jangan memberi satu akun semua izin. Untuk fungsi yang mengubah parameter penting, tambahkan timelock agar pengguna punya waktu bereaksi. Untuk nilai besar, gunakan multisig, bukan satu private key.

                  Akses.sol
                  // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Akses {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    mapping(bytes32 => mapping(address => bool)) public roles;
    address public admin;

    error TidakBerhak();

    constructor() {
        admin = msg.sender;
        roles[MINTER_ROLE][msg.sender] = true;
        roles[PAUSER_ROLE][msg.sender] = true;
    }

    modifier onlyRole(bytes32 role) {
        if (!roles[role][msg.sender]) revert TidakBerhak();
        _;
    }

    function beriRole(bytes32 role, address akun) external {
        require(msg.sender == admin, "bukan admin");
        roles[role][akun] = true;
    }

    function mint(address to) external onlyRole(MINTER_ROLE) {
        // logika mint
    }
}

                  Ini versi sederhana untuk memahami konsep. Untuk produksi, pakai AccessControl dan AccessControlEnumerable dari OpenZeppelin yang sudah menangani detail seperti role admin dan renounce.

                  Randomness dan oracle

                  Kontrak tidak punya sumber acak. Semua angka on-chain bisa diketahui sebelum transaksi dieksekusi. Untuk lotre, mint acak, atau distribusi NFT, gunakan Chainlink VRF atau commit-reveal dengan insentif yang benar. Untuk harga, gunakan feed yang terdesentralisasi, periksa heartbeat dan decimals, dan jangan memakai harga spot dari satu DEX sebagai oracle tunggal.

                  Upgrade dan delegatecall

                  Kontrak tidak bisa diganti, tetapi pola proxy bisa mengarahkan panggilan ke implementasi baru. Proxy menyimpan state, implementasi menyimpan logika. Karena delegatecall menjalankan kode implementasi dengan storage proxy, urutan slot harus sama persis. Kesalahan layout bisa menimpa owner atau saldo.

                  Jangan membuat proxy sendiri kecuali benar-benar perlu. Gunakan pola yang sudah teruji seperti UUPS atau Transparent Proxy dari OpenZeppelin, dan pahami bahwa upgrade berarti pengguna harus mempercayai siapa pun yang memegang izin upgrade. Untuk banyak aplikasi, kontrak immutable lebih jujur dan lebih aman.

                  Checklist sebelum deploy

                  • Apakah setiap fungsi yang mengubah state punya kontrol akses yang jelas?
                  • Apakah semua panggilan eksternal terjadi setelah state diperbarui?
                  • Apakah dana bisa terkunci karena satu penerima menolak ETH?
                  • Apakah loop bisa dibuat sangat panjang oleh pengguna?
                  • Apakah harga atau data eksternal bisa dimanipulasi dalam satu transaksi?
                  • Apakah ada tempat yang memakai tx.origin untuk otorisasi?
                  • Apakah casting ke tipe kecil sudah diperiksa?
                  • Apakah event mencatat perubahan penting agar bisa diaudit?
                  • Apakah test mencakup jalur gagal, bukan hanya jalur bahagia?
                  • Apakah kontrak sudah diuji dengan fuzz dan invariant?
                  • Apakah ada rencana jika bug ditemukan setelah deploy?
                  • Apakah kode dan parameter deploy sudah diverifikasi di explorer?
                  Audit bukan jaminan

                  Audit mengurangi risiko, bukan menghilangkannya. Banyak protokol yang diaudit tetap dieksploitasi karena perubahan kode setelah audit, kesalahan konfigurasi, atau desain ekonomi. Gunakan bug bounty, timelock, monitoring, dan batas kerugian yang eksplisit.

                  Latihan

                  Temukan dua masalah pada potongan ini: function ambil() external { require(tx.origin == owner); payable(msg.sender).transfer(address(this).balance); }

                  Lihat jawaban

                  Pertama, tx.origin bisa dieksploitasi lewat phishing: pengguna mengklik kontrak penyerang yang memanggil fungsi ini, dan tx.origin tetap pengguna. Gunakan msg.sender. Kedua, mengirim seluruh saldo tanpa memperbarui akuntansi dan memakai transfer dengan batas gas 2300 berisiko gagal untuk penerima kontrak. Selain itu, tidak ada pengecekan jumlah dan tidak ada pola pull payment. Gunakan CEI, call, dan accounting per pengguna.

                  Proyek 1: Counter.

                  Counter terlihat sepele, tetapi ia memuat hampir semua pertanyaan desain: siapa yang boleh mengubah, bagaimana perubahan dicatat, dan bagaimana cara mengujinya.

                  • Menulis kontrak state minimal dengan event dan akses.
                  • Membedakan increment publik dan operasi khusus owner.
                  • Menguji jalur berhasil dan jalur revert.
                  • Memperluas kontrak tanpa merusak invariant.

                  Spesifikasi

                  • Semua orang boleh menambah hitungan satu per satu.
                  • Hanya owner yang boleh mengurangi dan mereset.
                  • Hitungan tidak boleh di bawah nol.
                  • Setiap perubahan memancarkan event dengan nilai baru dan pengubahnya.
                  • Owner ditetapkan saat deploy dan tidak bisa diganti.
                  src/Counter.sol
                  // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Counter {
    uint256 public count;
    address public immutable owner;

    event CountChanged(uint256 indexed newCount, address indexed by);
    error NotOwner(address caller);
    error AlreadyZero();

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner(msg.sender);
        _;
    }

    function increment() external {
        count += 1;
        emit CountChanged(count, msg.sender);
    }

    function decrement() external onlyOwner {
        if (count == 0) revert AlreadyZero();
        count -= 1;
        emit CountChanged(count, msg.sender);
    }

    function reset() external onlyOwner {
        count = 0;
        emit CountChanged(0, msg.sender);
    }

    function read() external view returns (uint256) {
        return count;
    }
}

                  count sudah otomatis punya getter publik, jadi read() sebenarnya duplikat. Saya biarkan sebagai contoh bahwa fungsi view bisa memberi nama yang lebih ekspresif atau melakukan perhitungan tambahan. Untuk kontrak produksi, jangan menambah permukaan API tanpa alasan.

                  Proyek 2: Todo List.

                  Todo list adalah latihan terbaik untuk mapping, struct, dan event. Ia juga menunjukkan batas blockchain: menyimpan teks panjang on-chain itu mahal dan sering tidak perlu.

                  • Menggabungkan mapping, struct, array id, dan modifier.
                  • Membedakan data per pengguna dan data global.
                  • Membuat event yang cukup untuk aplikasi.
                  • Menilai kapan teks sebaiknya disimpan off-chain.

                  Spesifikasi

                  • Setiap pengguna punya daftar todo sendiri.
                  • Teks maksimal 140 byte, tidak boleh kosong.
                  • Pemilik bisa menambah, menandai selesai, dan menghapus.
                  • Setiap todo punya id yang stabil dan tidak dipakai ulang.
                  • Aplikasi bisa membaca satu todo atau seluruh todo milik satu pengguna.
                  src/TodoList.sol
                  // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract TodoList {
    struct Todo {
        uint256 id;
        string text;
        bool done;
        uint64 createdAt;
    }

    // pengguna => id => todo
    mapping(address => mapping(uint256 => Todo)) private todos;

    // pengguna => daftar id miliknya
    mapping(address => uint256[]) private ids;

    // id berikutnya per pengguna
    mapping(address => uint256) public nextId;

    event TodoCreated(address indexed owner, uint256 indexed id, string text);
    event TodoToggled(address indexed owner, uint256 indexed id, bool done);
    event TodoRemoved(address indexed owner, uint256 indexed id);

    error TextKosong();
    error TextTerlaluPanjang();
    error TodoTidakAda();

    modifier onlyTodoOwner(uint256 id) {
        if (todos[msg.sender][id].id == 0) revert TodoTidakAda();
        _;
    }

    function create(string calldata text) external returns (uint256 id) {
        uint256 panjang = bytes(text).length;
        if (panjang == 0) revert TextKosong();
        if (panjang > 140) revert TextTerlaluPanjang();

        id = ++nextId[msg.sender];         // mulai dari 1
        todos[msg.sender][id] = Todo({
            id: id,
            text: text,
            done: false,
            createdAt: uint64(block.timestamp)
        });
        ids[msg.sender].push(id);

        emit TodoCreated(msg.sender, id, text);
    }

    function toggle(uint256 id) external onlyTodoOwner(id) {
        Todo storage todo = todos[msg.sender][id];
        todo.done = !todo.done;
        emit TodoToggled(msg.sender, id, todo.done);
    }

    function remove(uint256 id) external onlyTodoOwner(id) {
        delete todos[msg.sender][id];

        uint256[] storage daftar = ids[msg.sender];
        for (uint256 i = 0; i < daftar.length; i++) {
            if (daftar[i] == id) {
                daftar[i] = daftar[daftar.length - 1];
                daftar.pop();
                break;
            }
        }

        emit TodoRemoved(msg.sender, id);
    }

    function get(address owner, uint256 id)
        external
        view
        returns (Todo memory)
    {
        return todos[owner][id];
    }

    function list(address owner)
        external
        view
        returns (Todo[] memory hasil)
    {
        uint256[] storage daftar = ids[owner];
        hasil = new Todo[](daftar.length);

        for (uint256 i = 0; i < daftar.length; i++) {
            hasil[i] = todos[owner][daftar[i]];
        }
    }

    function count(address owner) external view returns (uint256) {
        return ids[owner].length;
    }
}

                  Perhatikan penggunaan uint64(block.timestamp). Timestamp saat ini muat di uint64 untuk waktu yang sangat lama, dan menyimpannya lebih kecil dari uint256. Packing dengan bool done dan uint256 id tetap tidak banyak menolong karena string memaksa layout sendiri, tetapi biasakan memilih ukuran yang masuk akal.

                  Kenapa id per pengguna

                  Id yang dimulai dari 1 untuk setiap pengguna membuat penanda "tidak ada" menjadi jelas: id == 0 berarti tidak ada. Kalau satu penghitung global dipakai, dua pengguna bisa memiliki id berbeda dan relasi antar data lebih rumit. Konsekuensinya, id tidak unik secara global. Kalau aplikasi butuh id global, gunakan penghitung global atau pasangan (owner, id).

                  Gas dan batas desain

                  Menyimpan string 140 byte ke storage bisa memakai beberapa slot. list() mengembalikan seluruh todo dan menyalin semuanya ke memory. Kalau satu pengguna punya ratusan todo, fungsi ini bisa kehabisan gas saat dipanggil dari kontrak lain, meskipun pemanggilan view dari luar biasanya hanya dibatasi RPC provider. Untuk aplikasi nyata, pertimbangkan:

                  • Simpan teks di IPFS atau database, on-chain hanya hash dan status.
                  • Tambahkan pagination: list(owner, offset, limit).
                  • Pisahkan data yang perlu konsensus dari data yang hanya perlu ditampilkan.

                    Proyek 3: Voting.

                    Voting on-chain mudah ditulis, tetapi sulit dibuat adil. Siapa yang boleh memilih, bagaimana mencegah suara ganda, dan apa yang terjadi saat seri, semuanya keputusan desain.

                    • Menyimpan proposal dan suara dengan struct dan array.
                    • Membatasi waktu pemungutan suara.
                    • Mencegah satu alamat memilih dua kali.
                    • Menjelaskan batas privasi dan desentralisasi voting on-chain.

                    Spesifikasi

                    • Pembuat kontrak menentukan daftar proposal dan durasi voting.
                    • Satu alamat, satu suara.
                    • Voting ditutup setelah timestamp batas.
                    • Setelah ditutup, siapa pun bisa memanggil finalize sekali.
                    • Pemenang adalah proposal dengan suara terbanyak; seri dimenangkan proposal yang lebih dulu terdaftar.
                    src/Voting.sol
                    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Voting {
    struct Proposal {
        string name;
        uint256 votes;
    }

    Proposal[] public proposals;
    mapping(address => bool) public hasVoted;

    address public immutable chairperson;
    uint256 public immutable deadline;
    bool public finalized;
    uint256 public winningProposalId;

    event VoteCast(address indexed voter, uint256 indexed proposalId);
    event Finalized(uint256 indexed proposalId, string name, uint256 votes);

    error VotingClosed();
    error AlreadyVoted();
    error InvalidProposal();
    error AlreadyFinalized();
    error InvalidDuration();

    constructor(string[] memory names, uint256 durationSeconds) {
        if (names.length == 0 || names.length > 50) revert InvalidProposal();
        if (durationSeconds == 0) revert InvalidDuration();

        chairperson = msg.sender;
        deadline = block.timestamp + durationSeconds;

        for (uint256 i = 0; i < names.length; i++) {
            proposals.push(Proposal(names[i], 0));
        }
    }

    function vote(uint256 proposalId) external {
        if (block.timestamp >= deadline) revert VotingClosed();
        if (hasVoted[msg.sender]) revert AlreadyVoted();
        if (proposalId >= proposals.length) revert InvalidProposal();

        hasVoted[msg.sender] = true;
        proposals[proposalId].votes += 1;

        emit VoteCast(msg.sender, proposalId);
    }

    function finalize() external {
        if (block.timestamp < deadline) revert VotingClosed();
        if (finalized) revert AlreadyFinalized();

        uint256 winner = 0;
        uint256 maxVotes = 0;

        for (uint256 i = 0; i < proposals.length; i++) {
            if (proposals[i].votes > maxVotes) {
                maxVotes = proposals[i].votes;
                winner = i;
            }
        }

        winningProposalId = winner;
        finalized = true;

        emit Finalized(winner, proposals[winner].name, maxVotes);
    }

    function proposalCount() external view returns (uint256) {
        return proposals.length;
    }

    function getProposals() external view returns (Proposal[] memory) {
        return proposals;
    }
}

                    Perhatikan bahwa finalize bisa dipanggil siapa saja setelah batas waktu. Itu disengaja: hasil tidak bergantung pada satu admin. Tetapi pemanggil pertama menentukan kapan hasil diumumkan, dan jika ada proposal baru ditambahkan setelah voting dimulai (tidak ada di kontrak ini), hasil bisa berubah. Karena itu daftar proposal dikunci saat konstruksi.

                    Batasan yang harus kamu sadari

                    • Tidak anonim. Setiap suara terhubung ke alamat dan terlihat publik. Untuk voting rahasia, kamu butuh kriptografi khusus atau sistem off-chain dengan bukti.
                    • Satu alamat bukan satu orang. Siapa pun bisa membuat banyak wallet. Tanpa sybil resistance, hasil mudah dimanipulasi.
                    • Tidak ada bobot. Satu alamat satu suara. Untuk voting berbasis token, gunakan snapshot dan cegah pinjam-meminjam token sesaat.
                    • Tidak ada delegasi. Pemilih tidak bisa mengalihkan suara. Menambah delegasi membuka masalah loop dan bobot ganda.
                    • Gas. Setiap suara adalah transaksi. Partisipasi bisa rendah karena biaya dan kerumitan wallet.

                    Proyek 4: Simple Wallet.

                    Wallet kontrak adalah tempat menyimpan ETH dengan aturan. Di sinilah reentrancy berhenti menjadi teori dan menjadi saldo yang benar-benar bisa hilang.

                    • Menerima deposit dan melacak saldo per pengguna.
                    • Menerapkan checks-effects-interactions dan guard.
                    • Menangani kegagalan transfer ETH.
                    • Memisahkan dana pengguna dari dana tak terduga.

                    Spesifikasi

                    • Setiap alamat bisa menyetor minimal 0,001 ETH.
                    • Saldo per pengguna dicatat di kontrak.
                    • Pengguna bisa menarik sebagian atau seluruh saldonya.
                    • Penarikan mengikuti CEI dan dilindungi guard.
                    • Owner bisa mengambil ETH yang masuk di luar akuntansi (forced ETH).
                    src/SimpleWallet.sol
                    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract SimpleWallet {
    address public immutable owner;
    uint256 public constant MIN_DEPOSIT = 0.001 ether;

    mapping(address => uint256) public balanceOf;
    uint256 public totalDeposits;

    bool private locked;

    event Deposited(address indexed from, uint256 amount);
    event Withdrawn(address indexed to, uint256 amount);
    event Swept(address indexed to, uint256 amount);

    error BelowMinimum();
    error InsufficientBalance();
    error TransferFailed();
    error ReentrantCall();
    error NotOwner();

    constructor() {
        owner = msg.sender;
    }

    modifier nonReentrant() {
        if (locked) revert ReentrantCall();
        locked = true;
        _;
        locked = false;
    }

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner();
        _;
    }

    receive() external payable {
        _deposit();
    }

    function deposit() external payable {
        _deposit();
    }

    function _deposit() private {
        if (msg.value < MIN_DEPOSIT) revert BelowMinimum();
        balanceOf[msg.sender] += msg.value;
        totalDeposits += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function withdraw(uint256 amount) external nonReentrant {
        uint256 available = balanceOf[msg.sender];
        if (amount == 0 || amount > available) revert InsufficientBalance();

        // effects sebelum interaction
        balanceOf[msg.sender] = available - amount;
        totalDeposits -= amount;

        (bool ok, ) = payable(msg.sender).call{value: amount}("");
        if (!ok) revert TransferFailed();

        emit Withdrawn(msg.sender, amount);
    }

    // ETH yang dipaksa masuk (selfdestruct / block reward) tidak masuk akuntansi.
    // Owner boleh mengambil kelebihan, bukan dana pengguna.
    function sweepExtra() external onlyOwner {
        uint256 extra = address(this).balance - totalDeposits;
        if (extra == 0) return;
        (bool ok, ) = payable(owner).call{value: extra}("");
        if (!ok) revert TransferFailed();
        emit Swept(owner, extra);
    }
}

                    sweepExtra memakai selisih antara saldo kontrak dan total kewajiban. Kalau ada bug yang membuat totalDeposits lebih besar dari saldo, pengurangan akan underflow dan revert. Itu lebih baik daripada mengirim dana pengguna secara diam-diam. Namun invariant ini harus diuji dengan fuzz: saldo kontrak harus selalu setidaknya sebesar total deposit.

                    Kenapa tidak memakai transfer

                    transfer hanya memberikan 2300 gas ke penerima. Kontrak penerima yang punya logika receive sedikit lebih berat akan gagal, sehingga pengguna tidak bisa menarik dananya. call meneruskan gas dan mengembalikan status, sehingga kamu bisa menangani kegagalan dengan jelas.

                    Namun call membuka pintu reentrancy. Karena itu guard dan CEI wajib. Guard saja tidak cukup jika ada jalur lain yang tidak memakai guard. Urutan state-first adalah pertahanan utama.

                    Bab 15PROYEK

                    Proyek 5: Basic Token.

                    Menulis ERC-20 dari nol adalah ritual wajib. Setelah kamu merasakan sendiri allowance dan event, kamu akan mengerti kenapa OpenZeppelin ada, dan apa yang sebenarnya kamu warisi.

                    Kontrak lengkap

                    src/BasicToken.sol
                    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract BasicToken {
    string public name;
    string public symbol;
    uint8 public constant decimals = 18;

    uint256 public totalSupply;
    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    error ZeroAddress();
    error InsufficientBalance();
    error InsufficientAllowance();

    constructor(string memory nama, string memory simbol, uint256 supplyAwal) {
        name = nama;
        symbol = simbol;

        uint256 supply = supplyAwal * (10 ** uint256(decimals));
        totalSupply = supply;
        balanceOf[msg.sender] = supply;

        emit Transfer(address(0), msg.sender, supply);
    }

    function transfer(address to, uint256 value) external returns (bool) {
        _transfer(msg.sender, to, value);
        return true;
    }

    function approve(address spender, uint256 value) external returns (bool) {
        allowance[msg.sender][spender] = value;
        emit Approval(msg.sender, spender, value);
        return true;
    }

    function transferFrom(
        address from,
        address to,
        uint256 value
    ) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed < value) revert InsufficientAllowance();

        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - value;
        }

        _transfer(from, to, value);
        return true;
    }

    function _transfer(address from, address to, uint256 value) private {
        if (to == address(0)) revert ZeroAddress();

        uint256 balance = balanceOf[from];
        if (balance < value) revert InsufficientBalance();

        unchecked {
            balanceOf[from] = balance - value;
        }
        balanceOf[to] += value;

        emit Transfer(from, to, value);
    }
}

                    Beberapa detail penting:

                    • value dalam unit terkecil. Karena decimals = 18, satu token adalah 10**18 unit. Jangan mencampur tampilan desimal dengan nilai on-chain.
                    • supplyAwal * 10 ** 18 bisa overflow untuk angka besar, tetapi pada 0.8 akan revert. Batasi supply agar masuk akal.
                    • type(uint256).max dipakai sebagai allowance tak terbatas, sehingga transferFrom tidak perlu menulis ulang setiap kali. Ini penghematan gas yang umum, tetapi juga berarti izin tidak pernah berkurang.
                    • Transfer ke address(0) ditolak. Standar ERC-20 tidak mewajibkan ini, tetapi banyak implementasi melakukannya untuk mencegah token terbakar tanpa event burn yang jelas.
                    • Event Transfer dipancarkan saat mint awal dari address(0), sesuai konvensi standar.

                    Kenapa produksi memakai OpenZeppelin

                    Kontrak di atas cukup untuk belajar, tetapi belum memenuhi seluruh ekspektasi ekosistem. OpenZeppelin menyediakan implementasi yang sudah melalui audit, menangani kasus tepi, dan menambahkan ekstensi seperti burn, mint, cap, pause, permit, dan snapshot. Perbandingan lengkap ada di Bab 19.

                    Yang tidak boleh kamu lakukan adalah menyalin ERC-20 dari tutorial dan menganggapnya aman. Bug pada token bisa mengunci dana di DEX, merusak integrasi, atau membuka celah allowance. Gunakan library, lalu tulis test untuk perilaku tambahanmu.

                    Jembatan ke standar

                    Di Bab 16 kamu akan melihat spesifikasi ERC-20 dari sisi integrasi, bukan hanya sisi implementasi. Fokusnya: apa yang dijanjikan interface kepada wallet, DEX, dan kontrak lain, serta bagian mana yang sering disalahartikan.

                    Bab 16STANDAR

                    ERC-20: fungible token.

                    ERC-20 bukan kontrak. Ia janji antarmuka: enam fungsi dan dua event yang membuat token bisa dipakai wallet, DEX, dan kontrak lain tanpa saling mengenal.

                    • Membaca interface ERC-20 dan arti setiap fungsi.
                    • Menjelaskan alur approve dan transferFrom.
                    • Mengenali race condition allowance.
                    • Memilih ekstensi OpenZeppelin yang tepat.

                    Janji standar

                    Interface minimum ERC-20. Semua nilai dalam unit terkecil token, bukan jumlah token yang ditampilkan.
                    FungsiArtiCatatan integrasi
                    totalSupply()Jumlah token yang beredarHarus konsisten dengan jumlah saldo
                    balanceOf(address)Saldo satu alamatAlamat nol biasanya 0
                    transfer(address,uint256)Kirim dari pemanggilMengembalikan bool
                    allowance(address,address)Batas yang diberikan pemilik ke spenderBukan saldo, hanya izin
                    approve(address,uint256)Set izin untuk spenderMenimpa nilai sebelumnya
                    transferFrom(address,address,uint256)Kirim atas nama pemilikMengurangi allowance kecuali max

                    Dua event wajib: Transfer(from, to, value) dan Approval(owner, spender, value). Indexer, wallet, dan explorer mengandalkan event ini. Kontrak yang mengubah saldo tanpa memancarkan Transfer akan tampak rusak di UI meskipun state-nya benar.

                    Alur approve dan transferFrom

                    1. Pemilik memberi izin

                      Alice memanggil approve(dex, 100). Tidak ada token yang berpindah. Hanya allowance yang berubah.

                    2. Spender menarik token

                      DEX memanggil transferFrom(alice, pool, 40). Kontrak memeriksa allowance Alice ke DEX, mengurangi allowance, lalu memindahkan token.

                    3. Allowance tersisa

                      Jika bukan max, allowance menjadi 60. Jika max, nilai tidak berkurang dan izin tetap terbuka sampai dicabut.

                    Allowance adalah izin, bukan escrow. Token tetap di wallet Alice sampai spender memanggil transferFrom.

                    Masalah klasik: approve race

                    Bayangkan Alice sudah memberi DEX izin 100, lalu ingin mengubahnya menjadi 50. Ia mengirim approve(dex, 50). Spender yang melihat transaksi ini di mempool bisa lebih dulu menarik 100 dengan allowance lama, lalu setelah approve dieksekusi masih punya izin 50. Total yang bisa diambil 150, bukan 50.

                    Solusi umum: set allowance ke 0 dulu, lalu set nilai baru. Cara lain adalah increaseAllowance/decreaseAllowance, tetapi OpenZeppelin v5 menghapus helper itu dari ERC20 karena tidak sepenuhnya menyelesaikan masalah. Untuk pengalaman pengguna modern, gunakan permit (EIP-2612) yang menandatangani izin secara off-chain, atau minta pengguna mencabut izin lama lewat UI.

                    Implementasi OpenZeppelin

                    src/TokenBelajar.sol
                    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ERC20Burnable} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";
import {ERC20Capped} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Capped.sol";
import {ERC20Pausable} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Pausable.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract TokenBelajar is ERC20, ERC20Burnable, ERC20Capped, ERC20Pausable, Ownable {
    constructor()
        ERC20("Belajar Token", "BLJ")
        ERC20Capped(1_000_000 * 10 ** 18)
        Ownable(msg.sender)
    {
        _mint(msg.sender, 100_000 * 10 ** 18);
    }

    function mint(address to, uint256 amount) external onlyOwner {
        _mint(to, amount);
    }

    function pause() external onlyOwner {
        _pause();
    }

    function unpause() external onlyOwner {
        _unpause();
    }

    // OpenZeppelin v5 memakai _update sebagai hook transfer
    function _update(address from, address to, uint256 value)
        internal
        override(ERC20, ERC20Capped, ERC20Pausable)
    {
        super._update(from, to, value);
    }
}

                    Urutan pewarisan penting untuk hook. Di OpenZeppelin v5, ERC20Capped memeriksa batas pada _update saat mint, dan ERC20Pausable memblokir transfer saat pause. Kamu harus meng-override _update dan menyebut semua induk yang mengimplementasikannya. Kalau lupa salah satu, fitur itu tidak berjalan.

                    Perhatikan Ownable(msg.sender). Di OpenZeppelin v5, constructor Ownable membutuhkan alamat awal. Ini perubahan dari v4 yang tidak memerlukan argumen. Selalu baca versi library yang kamu pakai, jangan mencampur contoh dari tutorial lama.

                    Ekstensi yang sering dipakai

                    • ERC20Burnable: pemilik token bisa membakar miliknya, dan siapa pun dengan allowance bisa membakar atas nama orang lain.
                    • ERC20Capped: batas maksimum supply. Mint di atas cap akan revert.
                    • ERC20Pausable: menghentikan transfer saat darurat. Keputusan trust: pengguna harus percaya pada pauser.
                    • ERC20Permit: izin lewat signature EIP-2612, menghemat satu transaksi approve.
                    • ERC20Snapshot (di paket terpisah atau implementasi sendiri): menyimpan saldo pada blok tertentu untuk voting.
                    • ERC20Votes: bobot suara dengan delegation dan checkpoint.

                    Jebakan integrasi

                    • Fee-on-transfer. Token yang memotong biaya saat transfer membuat jumlah yang diterima lebih kecil dari value. Kontrak yang menghitung berdasarkan value bisa salah accounting.
                    • Rebasing. Saldo berubah tanpa transfer. Integrasi yang menyimpan saldo sebagai cache akan usang.
                    • Token dengan dua address. Beberapa proyek punya dua kontrak untuk simbol yang sama. Verifikasi alamat resmi.
                    • Decimals berbeda. Jangan hardcode 18 untuk semua token. Baca decimals() dan normalisasi.
                    • Return value aneh. Sebagian token lama tidak mengembalikan bool. Gunakan SafeERC20.

                      Bab 17STANDAR

                      ERC-721: NFT.

                      ERC-721 memberi setiap token id yang unik. Yang kamu miliki bukan gambar, tetapi catatan kepemilikan sebuah id. Gambar dan metadata hidup di tempat lain, dan bisa hilang.

                      • Membedakan kepemilikan token dan isi metadata.
                      • Menjelaskan alur mint, approve, dan safeTransferFrom.
                      • Menyusun metadata JSON dan tokenURI.
                      • Menilai biaya storage dan risiko tautan mati.

                      Satu id, satu pemilik

                      ERC-721 melacak pemilik setiap tokenId. Interface intinya mencakup ownerOf, balanceOf, transferFrom, safeTransferFrom, approve, setApprovalForAll, dan tokenURI. Event Transfer mencatat perpindahan, dan Approval mencatat izin.

                      Berbeda dari ERC-20, saldo tidak dipecah. Kamu memiliki token tertentu, bukan "sebagian" dari token. Karena itu NFT cocok untuk koleksi, tiket, domain, atau posisi yang unik, tetapi tidak untuk mata uang.

                      Metadata: apa yang sebenarnya dibeli

                      tokenURI(tokenId) mengembalikan URI, biasanya ipfs://... atau https://.... URI itu menunjuk ke JSON dengan nama, deskripsi, gambar, dan atribut. Kontrak tidak menyimpan gambar. Kalau penyimpanan off-chain mati, NFT tetap ada tetapi metadata bisa hilang.

                      metadata.json
                      {
  "name": "Kontrak #1",
  "description": "NFT latihan dari docs Solidity.",
  "image": "ipfs://bafy.../1.png",
  "attributes": [
    { "trait_type": "Level", "value": 1 },
    { "trait_type": "Tema", "value": "storage" }
  ]
}

                      Untuk koleksi kecil, kamu bisa memakai on-chain metadata dengan data URI. Itu mahal tetapi tidak bergantung pada server. Untuk koleksi besar, simpan gambar di IPFS atau Arweave dan kunci URI di kontrak. Pastikan ada rencana pinning dan biaya jangka panjang.

                      Kontrak mint dengan OpenZeppelin

                      src/Koleksi.sol
                      // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC721} from "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import {ERC721URIStorage} from "@openzeppelin/contracts/token/ERC721/extensions/ERC721URIStorage.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract Koleksi is ERC721URIStorage, Ownable {
    uint256 private _nextId = 1;
    uint256 public constant MAX_SUPPLY = 100;
    uint256 public mintPrice = 0.01 ether;

    error SoldOut();
    error WrongPayment();

    constructor()
        ERC721("Koleksi Belajar", "KBL")
        Ownable(msg.sender)
    {}

    function mint(string calldata uri) external payable returns (uint256 id) {
        if (_nextId > MAX_SUPPLY) revert SoldOut();
        if (msg.value != mintPrice) revert WrongPayment();

        id = _nextId++;
        _safeMint(msg.sender, id);
        _setTokenURI(id, uri);
    }

    function setMintPrice(uint256 harga) external onlyOwner {
        mintPrice = harga;
    }

    function withdraw() external onlyOwner {
        (bool ok, ) = payable(owner()).call{value: address(this).balance}("");
        require(ok, "withdraw gagal");
    }

    function totalMinted() external view returns (uint256) {
        return _nextId - 1;
    }
}

                      _safeMint memanggil onERC721Received jika penerima adalah kontrak. Ini mencegah NFT terkirim ke kontrak yang tidak bisa mengelolanya. Untuk mint ke EOA, tidak ada perbedaan. _setTokenURI berasal dari ERC721URIStorage, yang menyimpan URI per token di mapping tambahan dan menambah biaya storage.

                      Approval dan marketplace

                      Untuk menjual NFT, pemilik memberi izin ke marketplace: approve(marketplace, tokenId) untuk satu token, atau setApprovalForAll(operator, true) untuk seluruh koleksi. Marketplace kemudian memanggil transferFrom saat penjualan terjadi. Izin untuk semua token adalah risiko besar; cabut jika tidak lagi dipakai.

                      safeTransferFrom punya kelebihan dibanding transferFrom: ia memeriksa penerima kontrak. Namun cek itu menambah gas dan bisa gagal untuk kontrak yang tidak mengimplementasikan receiver. Gunakan safeTransferFrom untuk mengirim ke kontrak, dan pahami bahwa penolakan receiver adalah fitur, bukan bug.

                      Ekstensi yang umum

                      • ERC721Enumerable: menambah totalSupply, tokenByIndex, dan tokenOfOwnerByIndex. Membantu enumerasi, tetapi menambah biaya mint dan transfer.
                      • ERC721URIStorage: URI per token, bukan base URI global.
                      • ERC721Royalty (EIP-2981): info royalti untuk marketplace. Tidak otomatis menegakkan pembayaran.
                      • ERC721Pausable: menghentikan transfer saat darurat.
                      • ERC721Votes: bobot suara berdasarkan NFT, dengan delegation.

                      Lab 09

                      Mint dan pindahkan NFT

                      Mint token baru, lihat ownerOf dan tokenURI, lalu transfer atau beri approval. Setiap token punya id unik dan metadata contoh.

                      Belum ada NFT. Mint satu untuk memulai.

                        Metadata ditampilkan sebagai JSON contoh. Di kontrak nyata, URI menunjuk ke IPFS atau server, dan isinya tidak dijamin oleh blockchain.

                        Tautan bisa mati

                        NFT tidak menyimpan gambar. Kalau metadata hanya ada di server pribadi, koleksi bisa kehilangan isi saat server dimatikan. Sebelum membeli, periksa siapa yang menyimpan metadata, apakah sudah di-pin, dan apakah URI bisa diubah oleh owner kontrak.

                        Latihan

                        Kenapa safeMint bisa lebih aman, tetapi juga bisa membuat mint gagal untuk sebagian kontrak?

                        Lihat jawaban

                        safeMint memeriksa apakah penerima kontrak mengimplementasikan onERC721Received dan mengembalikan selector yang benar. Ini mencegah NFT terkunci di kontrak yang tidak bisa memindahkannya. Namun kontrak yang tidak mengimplementasikan receiver akan menolak mint, sehingga mint bisa gagal. Itu perilaku yang disengaja: lebih baik gagal daripada mengirim aset ke tempat yang tidak bisa mengelolanya.

                        Bab 18STANDAR

                        ERC-1155: multi-token.

                        ERC-1155 menyatukan fungible dan non-fungible dalam satu kontrak. Satu id bisa punya banyak salinan, id lain bisa unik, dan semuanya bisa dipindahkan sekaligus.

                        • Memahami model id => owner => balance.
                        • Memakai transfer batch untuk menghemat gas.
                        • Membedakan ERC-1155 dari ERC-20 dan ERC-721.
                        • Mengetahui batas dukungan marketplace dan wallet.

                        Satu kontrak, banyak jenis token

                        Pada ERC-721, setiap id unik dan hanya satu pemilik. Pada ERC-20, semua unit identik. ERC-1155 berada di tengah: setiap id punya supply sendiri, dan setiap alamat punya saldo untuk id itu. Id 1 bisa berupa 1.000 tiket biasa, id 2 bisa berupa 10 tiket VIP, dan id 3 bisa berupa satu karya seni unik dengan supply 1.

pragma solidity ^0.8.24;

import {ERC1155} from "@openzeppelin/contracts/token/ERC1155/ERC1155.sol";
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract ItemGame is ERC1155, Ownable {
    uint256 public constant GOLD = 1;
    uint256 public constant SILVER = 2;
    uint256 public constant PASS = 3;

    mapping(uint256 => uint256) public maxSupply;
    mapping(uint256 => uint256) public totalMinted;

    error SupplyHabis();

    constructor()
        ERC1155("https://api.contoh.com/item/{id}.json")
        Ownable(msg.sender)
    {
        maxSupply[GOLD] = 1_000;
        maxSupply[SILVER] = 10_000;
        maxSupply[PASS] = 100;
    }

    function mint(address to, uint256 id, uint256 amount) external onlyOwner {
        if (totalMinted[id] + amount > maxSupply[id]) revert SupplyHabis();
        totalMinted[id] += amount;
        _mint(to, id, amount, "");
    }

    function mintBatch(
        address to,
        uint256[] calldata ids,
        uint256[] calldata amounts
    ) external onlyOwner {
        for (uint256 i = 0; i < ids.length; i++) {
            if (totalMinted[ids[i]] + amounts[i] > maxSupply[ids[i]]) {
                revert SupplyHabis();
            }
            totalMinted[ids[i]] += amounts[i];
        }
        _mintBatch(to, ids, amounts, "");
    }

    function setURI(string calldata newUri) external onlyOwner {
        _setURI(newUri);
    }
}

                        _mintBatch lebih murah daripada memanggil _mint berkali-kali karena satu panggilan menghasilkan satu event batch dan mengurangi overhead. Namun ia tetap menulis saldo untuk setiap id. Untuk koleksi besar, pertimbangkan harga dan batas block gas.

                        Kapan memilih ERC-1155

                        • Kamu punya banyak jenis item dan ingin satu alamat kontrak.
                        • Pengguna sering memindahkan beberapa item sekaligus, dan kamu ingin menghemat gas.
                        • Sebagian id fungible dan sebagian unik dalam satu sistem.
                        • Kamu siap dengan kenyataan bahwa dukungan marketplace tidak seluas ERC-721.

                          Ownable atau AccessControl

                          Ownable

                          Satu owner. Cocok untuk prototipe, kontrak kecil, atau admin tunggal. Gunakan Ownable2Step agar transfer kepemilikan harus dikonfirmasi penerima.

                          AccessControl

                          Banyak role dengan izin berbeda. Cocok untuk tim: minter, pauser, treasury, upgrader. Setiap role punya admin role yang bisa mencabut.

                          src/Poin.sol
                          // SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ERC20Burnable} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";
import {ERC20Pausable} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Pausable.sol";
import {AccessControl} from "@openzeppelin/contracts/access/AccessControl.sol";

contract Poin is ERC20, ERC20Burnable, ERC20Pausable, AccessControl {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    constructor(address admin) ERC20("Poin Belajar", "PBL") {
        _grantRole(DEFAULT_ADMIN_ROLE, admin);
        _grantRole(MINTER_ROLE, admin);
        _grantRole(PAUSER_ROLE, admin);
    }

    function mint(address to, uint256 amount)
        external
        onlyRole(MINTER_ROLE)
    {
        _mint(to, amount);
    }

    function pause() external onlyRole(PAUSER_ROLE) {
        _pause();
    }

    function unpause() external onlyRole(PAUSER_ROLE) {
        _unpause();
    }

    function _update(address from, address to, uint256 value)
        internal
        override(ERC20, ERC20Pausable)
    {
        super._update(from, to, value);
    }
}

                          Perhatikan bahwa ERC20Pausable di OpenZeppelin v5 meng-override _update, sehingga kamu harus menyebutnya di daftar override. Kalau tidak, compiler akan menolak karena ada dua implementasi _update yang ambigu. Ini contoh bagus bahwa komposisi bukan sekadar menempel kontrak; hook harus dipahami.

                          SafeERC20 untuk token tidak standar

                          Sebagian token lama tidak mengembalikan bool dari transfer atau transferFrom. Memanggilnya dengan interface ERC-20 biasa bisa revert atau menafsirkan data dengan salah. SafeERC20 membungkus panggilan dan memeriksa hasilnya dengan aman.

pragma solidity ^0.8.24;

import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {SafeERC20} from "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract Kasir {
    using SafeERC20 for IERC20;

    function setor(IERC20 token, uint256 jumlah) external {
        token.safeTransferFrom(msg.sender, address(this), jumlah);
    }

    function kirim(IERC20 token, address to, uint256 jumlah) external {
        token.safeTransfer(to, jumlah);
    }
}

                          ReentrancyGuard

                          nonReentrant memakai satu slot status. Ia mencegah fungsi yang sama dipanggil ulang, tetapi tidak mencegah reentrancy lintas fungsi yang tidak memakai guard. Pasang guard pada semua fungsi yang memindahkan ETH atau memanggil kontrak eksternal, dan tetap terapkan CEI. Jangan mengandalkan guard sebagai pengganti desain yang benar.

                          Upgradeable contracts

                          Paket @openzeppelin/contracts-upgradeable menyediakan versi kontrak untuk pola proxy. Perbedaannya: constructor diganti initialize, dan implementasi tidak boleh memakai immutable untuk nilai yang perlu diubah. Kamu juga harus menjaga layout storage dan memakai __gap atau pola lain saat menambah variabel.

                          Upgrade membawa risiko governance: siapa yang bisa mengganti logika, berapa lama timelock, dan bagaimana pengguna diberi tahu. Kontrak immutable menghilangkan risiko ini dengan mengorbankan kemampuan memperbaiki bug. Pilih dengan sadar, bukan karena upgrade terdengar canggih.

                          Supply chain dan audit

                          • Impor hanya dari paket resmi dan versi yang dikunci. Periksa checksum atau lockfile.
                          • Jangan menyalin kode dari sumber acak ke folder src/ tanpa memahami lisensinya.
                          • Baca audit report untuk versi yang kamu pakai, bukan versi lain.
                          • Pantau pengumuman keamanan OpenZeppelin dan dependency lain.
                          • Untuk kontrak yang mengelola dana besar, tetap lakukan audit independen atas komposisimu, bukan hanya library-nya.
                          Komposisi juga bisa salah

                          OpenZeppelin mengamankan building block, bukan rancanganmu. Kombinasi Pausable, upgrade, dan access control bisa menciptakan kekuatan terpusat yang tidak kamu sadari. Tulis daftar siapa bisa melakukan apa, lalu uji setiap jalur.

                          Latihan

                          Kamu butuh token dengan supply tetap, bisa dibakar, dan bisa dijeda saat darurat. Kontrak OpenZeppelin apa saja yang kamu warisi, dan hook apa yang perlu di-override?

                          Lihat jawaban

                          ERC20, ERC20Burnable, ERC20Capped, ERC20Pausable, dan access control untuk pauser. Supply tetap bisa dicapai dengan cap dan tanpa fungsi mint, atau dengan mint sekali di constructor. Override _update dan sebut ERC20, ERC20Capped, serta ERC20Pausable. Uji bahwa mint di atas cap revert, transfer saat pause revert, dan burn mengurangi supply sekaligus saldo.

contract TokenInvariantTest is Test {

        uint256 total;
        for (uint256 i = 0; i < pengguna.length; i++) {

                          Frontend dengan ethers v6

                          app.js
                          import {BrowserProvider, Contract, parseUnits, formatUnits} from "ethers";

const ALAMAT = "0x...";
const ABI = [
  "function balanceOf(address) view returns (uint256)",
  "function transfer(address to, uint256 value) returns (bool)",
  "function decimals() view returns (uint8)"
];

export async function sambung() {
  const provider = new BrowserProvider(window.ethereum);
  await provider.send("eth_requestAccounts", []);
  const signer = await provider.getSigner();
  const token = new Contract(ALAMAT, ABI, signer);
  return {provider, signer, token};
}

export async function kirim(token, to, jumlah) {
  const decimals = await token.decimals();
  const value = parseUnits(jumlah, Number(decimals));
  const tx = await token.transfer(to, value);
  const receipt = await tx.wait();
  return receipt.hash;
}

export async function bacaSaldo(token, alamat) {
  const decimals = await token.decimals();
  const value = await token.balanceOf(alamat);
  return formatUnits(value, decimals);
}

                          Checklist kesiapan mainnet

                          • Semua test lulus, termasuk fuzz dan invariant.
                          • Kontrak sudah diuji di testnet dengan frontend nyata.
                          • Source code terverifikasi dan compiler settings terdokumentasi.
                          • Tidak ada private key, seed phrase, atau API key di repositori.
                          • Hak admin jelas, memakai multisig atau timelock bila perlu.
                          • Ada batas kerugian, pause, atau mekanisme darurat yang diuji.
                          • Parameter ekonomi (harga, cap, durasi) sudah dihitung.
                          • Audit atau setidaknya review independen untuk kontrak yang mengelola dana.
                          • Monitoring event dan saldo kontrak sudah disiapkan.
                          • Rencana komunikasi dan respons insiden sudah ditulis.
                          Deploy adalah transaksi biasa

                          Deploy memakai gas, bisa gagal, dan bisa menjadi mahal saat jaringan sibuk. Simulasikan dengan forge script tanpa --broadcast, periksa estimasi biaya, lalu deploy saat kondisi wajar. Jangan mengejar harga murah dengan menurunkan gas limit sampai transaksi gagal.

                          Kontrak lulus semua unit test, tetapi setelah deploy pengguna melaporkan transfer gagal untuk sebagian alamat. Apa tiga hal yang kamu periksa pertama?

Kedua, apakah ada pause, blacklist, atau batas transfer yang aktif. Ketiga, apakah ada perbedaan desimal atau allowance yang tidak diperbarui. Baca event dan revert reason di explorer, reproduksi di fork test dengan state nyata, lalu perbaiki lewat mekanisme yang tersedia, bukan menebak.

                          Glosarium dan cheatsheet.

                          Tempat kembali ketika istilah atau sintaks lupa. Bukan untuk dibaca sekali duduk.

                          Glosarium

                          ABI
                          Deskripsi antarmuka kontrak: nama fungsi, tipe parameter, dan return. Dipakai aplikasi untuk meng-encode panggilan.
                          Account abstraction
                          Desain yang membuat akun kontrak bisa bertindak seperti wallet, dengan aturan signature dan pembayaran gas sendiri.
                          Allowance
                          Jumlah token yang diizinkan pemilik untuk ditarik spender melalui transferFrom.
                          ABI encoding
                          Cara menyerialisasikan argumen fungsi menjadi data biner 32 byte per nilai sebelum dikirim ke EVM.
                          Bytecode
                          Kode mesin EVM hasil kompilasi Solidity. Disimpan di akun kontrak dan dieksekusi saat dipanggil.
                          Calldata
                          Data panggilan eksternal yang read-only dan paling murah untuk parameter fungsi external.
                          CEI
                          Checks-effects-interactions. Urutan aman: validasi, ubah state, baru panggil kontrak atau kirim ETH.
                          Custom error
                          Error yang dideklarasikan dengan error Nama(...). Lebih murah dan lebih terstruktur daripada string.
                          Delegatecall
                          Menjalankan kode kontrak lain di storage kontrak pemanggil. Dasar pola proxy, tetapi berisiko jika layout salah.
                          EIP
                          Ethereum Improvement Proposal. Standar dan perubahan protokol, misalnya EIP-20 untuk ERC-20 dan EIP-721 untuk NFT.
                          EOA
                          Externally owned account. Akun dengan private key yang bisa memulai transaksi.
                          Event
                          Log yang dipancarkan kontrak. Tidak bisa dibaca kontrak, tetapi bisa dibaca aplikasi dan explorer.
                          Fungible
                          Dapat dipertukarkan satu sama lain dengan nilai sama, seperti unit token.
                          Gas
                          Satuan biaya komputasi dan penyimpanan. Transaksi gagal tetap membayar gas yang terpakai.
                          Immutable
                          Variabel yang diisi sekali saat konstruksi dan disimpan di code, bukan storage.
                          Interface
                          Kontrak tanpa state dan implementasi, berisi deklarasi fungsi external untuk berkomunikasi.
                          Mapping
                          Struktur key-value tanpa iterasi dan tanpa length. Nilai yang belum diset mengembalikan default.
                          Memory
                          Area data sementara selama panggilan fungsi. Perubahan hilang setelah fungsi selesai.
                          Modifier
                          Potongan kode yang membungkus fungsi. Simbol _ menandai posisi badan fungsi.
                          msg.sender
                          Alamat pemanggil langsung. Bisa EOA atau kontrak. Jangan diganti dengan tx.origin untuk otorisasi.
                          msg.value
                          Jumlah wei yang dikirim bersama panggilan. Fungsi nonpayable akan revert jika nilainya lebih dari nol.
                          Nonce
                          Penghitung transaksi per akun, atau nilai anti-replay pada signature.
                          Payable
                          Menandai fungsi atau alamat yang boleh menerima ETH.
                          Proxy
                          Kontrak yang meneruskan panggilan ke implementasi lewat delegatecall. Memungkinkan upgrade dengan storage tetap.
                          Reentrancy
                          Serangan yang memanggil balik fungsi sebelum state selesai diperbarui, sering lewat penerimaan ETH.
                          Selector
                          Empat byte pertama hash signature fungsi, dipakai di calldata untuk menentukan fungsi yang dipanggil.
                          Storage
                          Penyimpanan persisten kontrak, terdiri dari slot 32 byte. Operasi tulis paling mahal.
                          Struct
                          Tipe data gabungan dengan beberapa field yang dideklarasikan bersama.
                          Total supply
                          Jumlah seluruh token yang beredar. Untuk token yang bisa mint atau burn, nilainya berubah dan harus dijaga konsisten.
                          tx.origin
                          Alamat EOA yang memulai rantai transaksi. Tidak aman untuk otorisasi karena bisa dieksploitasi lewat phishing.
